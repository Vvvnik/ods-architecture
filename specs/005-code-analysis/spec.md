# Спецификация: Анализ кода — детектор языков, оркестратор и парсеры

**Фича**: `005-code-analysis`

**Создано**: 2026-07-09

**Статус**: Реализовано (US1–US5, все 4 парсера, polish T061–T063)

**Вход**: Формализация post-MVP анализа кода: детектор языков, модульные парсеры,
оркестрация запуска, контракт envelope, UX подтверждения после sync.
Источник: `ods-help/requirements/data-model-persig-analysis-draft.md` (§3 D-005-*,
§3.1, §4, §5).

**Родительская спека**: `specs/001-ods-vision/spec.md` (этап 4)

**Зависимость**: `specs/002-domain-model/spec.md` (проект, sync, рабочая копия, дерево)

**Потребитель**: `specs/006-project-graph/spec.md` (ingest результатов парсеров в канонический граф)

## Краткое описание

После синхронизации рабочей копии проекта платформа **автоматически определяет языки**
исходного кода, показывает пользователю отчёт и **по явному подтверждению** запускает
**модульные парсеры** — отдельные исполняемые компоненты на каждый поддерживаемый язык.
Каждый парсер возвращает результат в **единой обёртке (envelope)** со **свободным
содержимым** внутри; оркестратор не интерпретирует внутреннюю структуру.
**Порядок запуска парсеров** определяется отчётом по языкам: первым идёт язык
с наибольшим `file_count`, далее по убыванию — **независимо** от языка backend
платформы. Результаты детектора и парсеров сохраняются как метаданные анализа;
слияние в канонический граф — в зоне ответственности `006`.

## Границы спеки

### Входит

- **Language Detector** после sync или импорта: обход рабочей копии, классификация
  файлов по языкам (расширения, shebang, манифесты проекта);
- **отчёт по языкам** с числом файлов, примерами путей и статусом парсера;
- **реестр парсеров** (идентификатор, поддерживаемые языки, команда запуска, версия схемы);
- **оркестратор** запуска модулей: порядок по отчёту, параллель/очередь, таймауты, логи;
- **контракт envelope** — общая обёртка результата парсера;
- **модульные парсеры** как отдельные CLI-процессы; целевой набор: TypeScript/JavaScript,
  C#, Python, C++ (модули поставляются по одному за инкремент разработки);
- **порядок запуска** парсеров при анализе — по отчёту (`file_count` убыв.), тот же
  что в UI; не по стеку платформы;
- **инкрементальный анализ** — повторный запуск только по изменённым файлам;
- **UX подтверждения** — два последовательных модальных окна после sync (языки → изменения);
- сохранение отчёта детектора и результатов парсеров в хранилище метаданных платформы.

### Не входит

- каноническая модель графа, ingest-адаптеры, индексы графа, API подграфа (`006-project-graph`);
- UI визуализации графа (замена заглушки «Граф» — в `006`);
- Graphify и его JSON-канал (`007`);
- RAG, векторный поиск, аутентификация;
- единый JSON-формат внутри поля `model` для всех парсеров;
- один монолитный JSON всего проекта из выходов парсеров;
- парсинг AST на этапе детектора (только классификация файлов);
- дублирование дерева файлов из `002` (используется существующее дерево и рабочая копия).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Автоопределение языков после sync (Priority: P1)

Как **разработчик**, после завершения sync я вижу, какие языки присутствуют в проекте,
сколько файлов каждого языка и есть ли для них парсер — без автоматического запуска анализа.

**Why this priority**: Детектор — первый шаг цепочки анализа; без него невозможно
осмысленно запускать парсеры и показывать статус в UI.

**Independent Test**: Sync репозитория с файлами нескольких языков → в хранилище
метаданных появляется отчёт: все обнаруженные языки, отсортированные по убыванию
числа файлов; для каждого языка — статус парсера (`available` / `missing` / `failed`).

**Acceptance Scenarios**:

1. **Given** проект с файлами `.ts`, `.py`, `.cpp`, `.go` после успешного sync,
   **When** детектор завершил работу, **Then** отчёт содержит все четыре языка;
   TypeScript, Python и C++ — со статусом `available` или `missing` в зависимости от
   наличия модуля; Go без модуля — `missing`; порядок языков — по `file_count` убыв.
2. **Given** два языка с одинаковым `file_count`, **When** формируется отчёт,
   **Then** при равном числе файлов языки упорядочены по имени (алфавит).
3. **Given** детектор завершился, **When** пользователь ещё не подтвердил анализ,
   **Then** парсеры **не** запускаются автоматически.
4. **Given** файл с нестандартным расширением, **When** в нём есть shebang или
   проектный манифест указывает на язык, **Then** детектор может отнести файл к языку
   по этим эвристикам (в дополнение к расширению).

### User Story 2 — Подтверждение анализа в UI (Priority: P1)

Как **разработчик**, я прохожу два шага подтверждения после sync: сначала просматриваю
языки проекта, затем — список изменений в коде — и только после этого запускаю парсеры.

**Why this priority**: Явное согласие пользователя предотвращает нежелательный
долгий анализ и даёт контроль над инкрементом.

**Independent Test**: После sync открывается окно 1 (языки) → «Продолжить» → окно 2
(изменения) → «Продолжить» → старт оркестратора; «Отмена» на любом шаге останавливает
цепочку без запуска парсеров. 

**Acceptance Scenarios**:

1. **Given** sync только что завершился, **When** отображается **окно 1 — языки**,
   **Then** список языков из отчёта (сверху — больше файлов); кнопки «Продолжить» и «Отмена».
2. **Given** **новый проект** (первый sync), **When** окно 1, **Then** языки показаны
   **без** подсветки «новизны» относительно прошлого анализа.
3. **Given** **повторный sync**, **When** окно 1, **Then** языки, появившиеся впервые,
   подсвечены **красным** (нет парсера) или **зелёным** (парсер есть).
4. **Given** пользователь нажал «Продолжить» в окне 1, **When** открывается **окно 2**,
   **Then** показаны изменения с прошлого sync: добавленные, изменённые, удалённые файлы.
5. **Given** окно 2, **When** «Продолжить», **Then** оркестратор запускает парсеры
   для языков со статусом `available`.
6. **Given** окно 1 или 2, **When** «Отмена», **Then** парсеры не запускаются;
   при отмене на шаге 2 сохраняется прежний результат анализа (если был).

### User Story 3 — Модульные парсеры и оркестрация (Priority: P1)

Как **платформа**, я запускаю только зарегистрированные парсер-модули для языков
с доступным парсером, получаю envelope-результаты и не падаю из-за отсутствующего модуля.

**Why this priority**: Ядро фичи — расширяемая архитектура «один язык — один модуль»
с единым контрактом на границе.

**Independent Test**: Репозиторий с TS, Python, C++, C# и Go → запускаются модули
для языков с `available`; для Go — `missing`, остальной анализ завершается успешно;
каждый модуль возвращает envelope с перечнем проанализированных файлов.

**Acceptance Scenarios**:

1. **Given** язык со статусом `available`, **When** оркестратор запускает модуль,
   **Then** модуль получает идентификатор проекта, корень рабочей копии и список файлов
   (или glob); возвращает envelope и код завершения.
2. **Given** язык со статусом `missing`, **When** оркестрация, **Then** модуль
   **не** вызывается; в отчёте/логах явный статус; другие парсеры продолжают работу.
3. **Given** модуль завершился с ошибкой, **When** оркестратор обрабатывает результат,
   **Then** статус языка — `failed`; остальные модули не блокируются.
4. **Given** несколько языков с `available`, **When** оркестрация, **Then** первым
   запускается парсер языка с **наибольшим** `file_count` в отчёте; далее — по
   убыванию (как в UI); язык backend платформы **не** получает приоритет, если у
   него меньше файлов, чем у других языков проекта.
5. **Given** успешный прогон модуля, **When** результат сохранён, **Then** envelope
   содержит обязательные поля: идентификатор парсера, версию схемы, идентификатор проекта,
   идентификатор прогона анализа, время генерации, список проанализированных путей,
   поле `model` (свободная структура); оркестратор **не** валидирует содержимое `model`.
6. **Given** N успешных модулей, **When** анализ завершён, **Then** в хранилище
   **N отдельных артефактов** (не один объединённый JSON всего проекта).

### User Story 4 — Инкрементальный анализ (Priority: P2)

Как **разработчик**, при повторном sync я анализирую только изменённые файлы,
а не весь репозиторий заново.

**Why this priority**: Сокращает время анализа на больших проектах; обязательно
в первой итерации `005` по согласованному черновику.

**Independent Test**: Первый полный анализ → правка одного файла → sync →
подтверждение в UI → парсер **соответствующего языка** получает только изменённый
файл (и связанные по правилам модуля, если применимо).

**Acceptance Scenarios**:

1. **Given** повторный sync, **When** определяются изменения относительно прошлого sync,
   **Then** список включает добавленные, изменённые и удалённые файлы (для показа в окне 2
   и для передачи парсерам).
2. **Given** пользователь подтвердил анализ после инкрементального sync,
   **When** запускаются парсеры, **Then** каждый модуль анализирует **только**
   затронутые файлы своего языка из списка изменений (не полный репозиторий).
3. **Given** первый sync проекта (нет предыдущего анализа), **When** запускается анализ,
   **Then** парсеры получают полный набор файлов соответствующих языков.

---

### User Story 5 — Поэтапная поставка парсер-модулей (Priority: P2)

Как **команда платформы**, мы подключаем парсер-модули по одному за инкремент
(TypeScript/JavaScript, C#, Python, C++); каждый новый модуль следует единому
контракту envelope и регистрируется в реестре без изменения оркестратора.

**Why this priority**: Снижает риск «большого взрыва»; первый **рабочий** прогон
возможен, как только в реестре есть модуль для языка, который окажется вверху
отчёта по `file_count` (или ниже — для языков с меньшим числом файлов, когда
их модуль появится).

**Independent Test**: Зарегистрирован один модуль (например, Python) → репозиторий,
где Python — язык с наибольшим `file_count` → после подтверждения envelope с
соответствующим `parser_id` и непустым `model` сохранён в хранилище; модули для
других языков со статусом `missing` не блокируют прогон.

**Acceptance Scenarios**:

1. **Given** модуль зарегистрирован в реестре и язык в отчёте со статусом `available`,
   **When** пользователь подтвердил анализ, **Then** модуль запускается в позиции
   языка в списке отчёта (по `file_count`) и возвращает валидный envelope.
2. **Given** модуль в каталоге парсеров, **When** проверяется реестр,
   **Then** у модуля есть манифест: `id`, `languages`, `schema_version`, `command`,
   описание входа (корень WC, файлы, project_id) и выхода (путь к envelope JSON).
3. **Given** репозиторий, где TypeScript — не доминирующий язык (меньше файлов,
   чем у C# или Python), **When** доступны модули для нескольких языков,
   **Then** первым **запускается** парсер языка с наибольшим `file_count`, а не
   TypeScript «по умолчанию».

---

### Edge Cases

- Пустой репозиторий или только бинарные/неизвестные файлы: отчёт без языков или с
  единственной категорией «неизвестно»; парсеры не запускаются; UI сообщает об отсутствии
  анализируемых языков.
- Sync завершился с `partial`/`failed`: детектор запускается только при наличии
  актуальной рабочей копии; при критической ошибке sync — понятное сообщение без зависания.
- Таймаут модуля: статус `failed` для языка, лог с причиной; оркестратор завершает прогон.
- Параллельный запуск sync и анализа: анализ не стартует до завершения sync (согласовано
  с блокировками операций проекта из `002`).
- Удаление проекта (`002` DELETE): артефакты анализа `005` в хранилище метаданных
  удаляются каскадно (согласовать детали индексов с `006`).
- Язык с `file_count` = 0 после фильтрации: не попадает в отчёт и не запускается.
- TypeScript — язык backend платформы, но в репозитории у него мало файлов: парсер TS
  запускается **после** языков с большим `file_count`, не первым.
- Повторное нажатие «Продолжить» или двойной запуск анализа: идемпотентность или
  явная блокировка «анализ уже выполняется» (как у sync).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST запускать **Language Detector** автоматически после
  успешного sync или импорта проекта (до запуска парсеров).
- **FR-002**: Детектор MUST классифицировать файлы рабочей копии по языкам, используя
  расширения и опционально shebang, `package.json`, `*.csproj` и аналогичные маркеры.
- **FR-003**: Детектор MUST формировать **отчёт по языкам** с полями: язык, число файлов,
  примеры путей, привязка к `parser_id` (или null), статус парсера (`available` /
  `missing` / `failed`).
- **FR-004**: Языки в отчёте MUST быть отсортированы по `file_count` по убыванию;
  при равенстве — по имени языка (алфавит).
- **FR-005**: Система MUST вести **реестр парсеров**: идентификатор, поддерживаемые языки,
  команда запуска, версия native-схемы (конфигурация или каталог модулей).
- **FR-006**: Каждый парсер MUST быть **отдельным исполняемым модулем** (CLI):
  вход — идентификатор проекта, корень рабочей копии, список файлов; выход — envelope JSON
  и код возврата.
- **FR-007**: Все парсеры MUST соблюдать **envelope-контракт**: `parser_id`, `schema_version`,
  `project_id`, `analysis_run_id`, `generated_at`, `files_analyzed[]`, `model` (свободный payload).
- **FR-008**: Оркестратор MUST запускать модули **только** для языков со статусом `available`,
  **строго в порядке** списка из отчёта детектора (`file_count` убыв., при равенстве —
  по имени языка); порядок MUST совпадать с UI (§3.1); MUST NOT давать приоритет языку
  backend платформы; MUST поддерживать очередь/параллель, таймауты и логирование.
- **FR-009**: Оркестратор MUST NOT требовать знания структуры поля `model` внутри envelope.
- **FR-010**: Целевые парсеры для поэтапной поставки: TypeScript/JavaScript, C#, Python, C++;
  языки без модуля MUST получать статус `missing` без падения всего анализа.
- **FR-011**: Система MUST поддерживать **инкрементальный анализ**: после sync определять
  изменённые файлы и передавать парсерам только их (при первом анализе — полный набор).
- **FR-012**: Отчёт детектора и результаты парсеров MUST сохраняться в **хранилище метаданных**
  платформы; исходники остаются только в рабочей копии на filesystem.
- **FR-013**: Система MUST NOT собирать один монолитный JSON всего проекта из выходов парсеров;
  на каждый успешный модуль — отдельный артефакт.
- **FR-014**: После sync UI MUST показывать **два модальных окна подряд** (языки → изменения);
  парсеры MUST запускаться только после двух подтверждений «Продолжить».
- **FR-015**: При «Отмена» на шаге 1 или 2 парсеры MUST NOT запускаться; при отмене на шаге 2
  прежний результат анализа MUST сохраняться.
- **FR-016**: Целевые модули (TypeScript/JavaScript, C#, Python, C++) MUST поставляться
  **по одному за инкремент** разработки; порядок поставки в `plan.md` **не** задаёт
  порядок запуска — runtime-порядок всегда из отчёта по `file_count` (FR-004, FR-008).
- **FR-017**: Каждый модуль в реестре MUST иметь манифест с полями: `id`, `languages`,
  `schema_version`, `command`, описание входных и выходных параметров.
- **FR-018**: Детектор MUST NOT выполнять полноценный AST-парсинг — только классификацию файлов.

### Key Entities

- **Отчёт по языкам (Language Report)**: снимок детектора для проекта — время обнаружения,
  список языков с числом файлов, примерами путей и статусом парсера; один документ на прогон
  детекции.
- **Прогон анализа (Analysis Run)**: логическая сессия от подтверждения пользователя до
  завершения всех модулей; идентификатор связывает envelope-артефакты (детали хранения — в `006`).
- **Envelope парсера**: стандартизированная обёртка результата модуля; единственная часть
  выхода, которую понимает оркестратор.
- **Native model**: содержимое поля `model` в envelope — формат определяется модулем и
  адаптером ingest (`006`), не оркестратором.
- **Запись реестра парсера**: описание модуля — идентификатор, языки, команда, версия схемы.
- **Список изменений (Change Set)**: файлы, добавленные, изменённые или удалённые с прошлого
  sync; основа для окна 2 и инкрементального запуска.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: После sync многиязычного репозитория пользователь видит полный отчёт по языкам
  в течение **30 секунд** для проектов до **10 000** файлов (пилотные объёмы).
- **SC-002**: Для репозитория с поддерживаемыми и неподдерживаемыми языками **100%**
  поддерживаемых языков с модулем `available` получают envelope-результат; неподдерживаемые —
  статус `missing` без сбоя остальных модулей.
- **SC-003**: При инкрементальном sync с изменением до **5%** файлов время анализа
  сокращается **не менее чем на 50%** по сравнению с полным повторным прогоном
  (на одном и том же проекте пилота).
- **SC-004**: **95%** пользователей пилота могут пройти цепочку «sync → окно языков →
  окно изменений → анализ» без обращения к документации (наблюдаемое UX-тестирование).
- **SC-005**: Добавление нового языкового модуля не требует изменения оркестратора
  кроме регистрации в реестре (проверяется подключением второго модуля из целевого набора).

## Assumptions

- Рабочая копия и дерево файлов уже поддерживаются `002`; детектор и парсеры используют
  тот же корень WC и идентификатор проекта.
- Хранилище метаданных платформы — то же, что для проектов и дерева (`002`); конкретные
  индексы и схемы документов для артефактов анализа уточняются в `006`, но `005` обязан
  производить данные в согласованном виде (отчёт по языкам, envelope).
- UX модальных окон реализуется в портале (`003`) по контракту этой спеки; backend
  предоставляет данные для окон и API запуска/статуса анализа.
- Определение изменённых файлов — через сравнение с предыдущим sync (например, diff
  рабочей копии); точный механизм — в `plan.md`, без изменения пользовательского сценария.
- Пилот без аутентификации; один пользователь на инстанс.
- Graphify (`007`) — отдельный канал, не входит в envelope языковых парсеров.
- Язык UI и сообщений — русский.
- **Порядок запуска vs поставка:** на ранних этапах обсуждался приоритет языка backend
  (TypeScript); **согласованное решение** — при анализе первым идёт язык с наибольшим
  `file_count` в отчёте; порядок поставки модулей в разработке — отдельное решение
  для `plan.md` и не переопределяет runtime-порядок.
- **FR-004 vs FR-008:** FR-004 — сортировка языков в отчёте; FR-008 — тот же порядок
  при запуске оркестратором (дублирование намеренное: отчёт и runtime разделены).
