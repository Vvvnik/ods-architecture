# Спецификация: Масштабирование пайплайна (large repo)

**Фича**: `010-scale-pipeline`

**Создано**: 2026-07-15

**Статус**: Уточнено; plan + tasks синхронизированы (2026-07-15). Дальше:
`/speckit-implement`.

**Вход**: Усиление пайплайна sync → детектор → оркестратор → парсеры →
ingest → хранилище графа → API/UI-списки под **крупные** репозитории
(класс enterprise .NET monorepo). Эталон масштаба для ручного smoke —
внешний путь (не коммитится в ODS). Canvas / React Flow — **не** в scope
этой фичи (→ `011-ods-graph-viewer`).

**Родительская спека**: `specs/001-ods-vision/spec.md` (этап 9)

**Зависимость**: `specs/005-code-analysis/spec.md`;
`specs/006-project-graph/spec.md`; `specs/007-portal-scale-ux/spec.md`;
`specs/008-code-graph-depth/spec.md`; `specs/009-system-landscape/spec.md`

## Краткое описание

После закрытия code- и system-слоёв (`005`–`009`) пилот на малых fixture
работает, но целевые репозитории — на порядки больше. Пользователь должен
получить **предсказуемый, корректный и достаточно быстрый** полный цикл
анализа на крупном дереве исходников **без** интерактивной схемы (canvas).
Эта фича — про устойчивость и масштаб пайплайна и списочного просмотра
графа, а не про новый UX-визуализатор.

## Границы спеки

### Входит

- устранение **повторных полных обходов** дерева рабочей копии на одном
  цикле sync+подготовки анализа: **ровно один** полный walk (обычно при
  sync) строит file inventory; детектор, change-set и смежные шаги
  MUST брать этот снимок, не обходя дерево заново;
- **измеримые** критерии готовности и quickstart: длительности этапов
  цикла (включая **сравнение full vs incremental** для SC-003), объём
  графа, прогон на `large-repo` fixture; **обязательный**
  ручной smoke на внешнем эталоне масштаба оператора (локальный путь вне
  репозитория ODS) — без коммита эталона, без обязательного Docker-mount
  и **без** требования CI;
- масштаб **C#-анализа**: много проектов / solution, таймауты, частичный
  успех (`partial`) с понятными результатами парсеров, инкремент без
  полного пересчёта всего репозитория без необходимости;
- масштаб **оркестрации**: контролируемый параллелизм и таймауты дочерних
  процессов, прозрачные статусы при `partial` / `failed` (hard RAM cap
  на subprocess **не** в MVP);
- масштаб **ingest / индексы графа**: пакетная запись, инкрементальные
  upsert/delete для code- и system-слоя, без «висячих» рёбер на
  несуществующие узлы;
- масштаб **API и списочного UI** графа: пагинация и поиск при большом
  числе узлов/рёбер (без canvas);
- **видимый прогресс** длительных операций sync и анализа для оператора
  (этапы / статус хода, чтобы не терять ориентир во времени).

**Отложено (обязательно зафиксировать, не MVP `010`):**

- общий CLI-контракт / SDK для парсеров (разбор аргументов + запись
  envelope) — follow-up после закрытия scale MVP; MUST NOT забыть.

### Не входит

- React Flow / canvas / layout графа (→ `011-ods-graph-viewer`);
- изменение семантики system-/code-слоя, новых парсеров артефактов
  (кроме необходимых правок для масштаба уже существующих модулей);
- правка требований и закрытие этапов `002`–`009` (зависимости только
  **потребляем**; спеку `009` **не** меняем);
- коммит внешнего эталона масштаба оператора или его копии в
  `docker/fixtures`;
- RAG, auth, редактирование/удаление узлов графа в UI;
- реализация общего parser CLI SDK в рамках DoD `010` (follow-up, см. US7);
- hard RAM cap / kill по порогу памяти на каждый subprocess (вне MVP);
- обязательный CI-прогон на внешнем эталоне (только ручной smoke
  по quickstart; не часть CI).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Один снимок файлов на цикл (Priority: P1)

Как **оператор платформы**, после sync и запуска анализа на большом
репозитории я уверен, что система **не сканирует** дерево рабочей копии
несколько раз независимо без нужды, и что детектор, change-set и связанные
шаги опираются на **один согласованный** снимок путей и метаданных файлов.

**Why this priority**: Повторные обходы — главный источник лишнего времени
и I/O на крупных деревьях; без этого остальной «масштаб» маскирует симптом.

**Independent Test**: На **large-repo** (≥1000 файлов) замерить число
полных обходов WC за один sync+подготовку анализа (DoD SC-002); детектор
и change-set дают согласованные множества путей.

**Acceptance Scenarios**:

1. **Given** крупный WC (large-repo class), **When** выполняется sync и
   строится отчёт детектора / change-set, **Then** на весь цикл
   sync+подготовки используется **не более одного** полного обхода
   дерева файлов: inventory создаётся при sync (или эквивалентный снимок),
   detector и change-set **не** выполняют повторный полный walk.
2. **Given** тот же WC, **When** сравнивают выборки путей детектора и
   change-set для одного snapshot moment, **Then** нет противоречий
   «файл есть у одного, отсутствует у другого» без изменения disk state.

---

### User Story 2 — Измеримый прогон, критерии готовности и прогресс (Priority: P1)

Как **команда ODS**, я могу по quickstart прогнать большой fixture, снять
длительности этапов (sync, детектор, прогон анализа, ingest) и размер
графа и **обязательно** зафиксировать ручной smoke на внешнем эталоне
масштаба перед закрытием этапа. Во время длинного прогона **оператор**
видит **ход работы** (прогресс по этапам), а не «зависание без сигнала».

**Why this priority**: Без SC и прогона «втемную» нельзя закрыть этап;
без прогресса на 15-минутном цикле легко принять нормальный прогон за hang.

**Independent Test**: Follow quickstart на `large-repo` (или
эквивалентном fixture); заполнить таблицу длительностей; критерий SC
выполняется или явно фиксируется regression.

**Acceptance Scenarios**:

1. **Given** инструкция quickstart, **When** выполняют полный цикл на
   large-repo fixture, **Then** в отчёте есть длительности sync, детектора,
   analysis run и ingest плюс counts узлов/рёбер.
2. **Given** внешний эталон масштаба доступен локально у оператора,
   **When** выполняется closing smoke по quickstart, **Then** шаги
   воспроизводимы **без** помещения эталона в git ODS и **без** CI;
   этап `010` **не** закрывается без зафиксированного результата этого
   smoke (успех или документированный `partial` с расшифровкой).
3. **Given** запущен sync или analysis run на large fixture, **When**
   оператор смотрит портал во время выполнения, **Then** виден
   актуальный статус: **текущий этап** (sync / детект / анализ / ingest
   или эквивалент) и при анализе — **активный парсер** и/или счётчик
   «N из M», с обновлением до завершения.

### User Story 3 — Крупный C# monorepo без «тихого» провала (Priority: P1)

Как **разработчик**, на репозитории с многими `.csproj` / solution я
получаю завершённый прогон: либо полный успех, либо **частичный** с
понятными статусами парсеров и таймаутами, а повторный прогон при
небольших изменениях **не** требует полного пересчёта всего дерева без
необходимости.

**Why this priority**: Целевой класс репозиториев — .NET; C# — главный
потребитель CPU/времени.

**Independent Test**: Fixture / репозиторий с несколькими проектами C#;
прогон завершается в пределах политики таймаутов; incremental меняет
только затронутые пути.

**Acceptance Scenarios**:

1. **Given** много проектов C# в WC, **When** запускают анализ,
   **Then** прогон не зависает бесконечно: таймаут или завершение с
   явным статусом парсера.
2. **Given** успешный прошлый прогон и изменение небольшого набора `.cs`,
   **When** повторный анализ, **Then** инкремент затрагивает затронутые
   пути; полный пересчёт всего репо **не** обязателен; wall-clock
   analysis+ingest быстрее full baseline не менее чем на **40%** **или**
   в отчёте/quickstart явно указано, почему инкремент недоступен.
3. **Given** сбой или таймаут одного парсера при успехе других, **When**
   смотрят итог прогона, **Then** статус `partial`/`failed` и перечень
   результатов парсеров позволяют понять, что упало.

### User Story 4 — Оркестрация под нагрузкой (Priority: P2)

Как **оператор**, при параллельном запуске нескольких парсеров на
крупном репо система соблюдает лимит параллелизма и таймауты дочерних
процессов и не оставляет «пустые» результаты без сообщения об ошибке.

**Why this priority**: Нужно после базовой корректности C# и снимка FS;
усиливает стабильность при реальном масштабе.

**Independent Test**: Прогон с несколькими code + system парсерами на
large fixture; соблюдены лимиты; все статусы в `parser_results`
заполнены.

**Acceptance Scenarios**:

1. **Given** настроенный лимит параллелизма N, **When** spawn M > N
   парсеров, **Then** одновременно выполняются не более N.
2. **Given** сбой или таймаут дочернего процесса, **When** прогон
   завершается, **Then** в результате есть понятный статус и сообщение
   для оператора (без «тихого» skip без причины).
3. **Given** политика MVP без hard RAM cap, **When** парсер падает по
   OOM ОС/runtime, **Then** это отражается как failed/partial с сообщением,
   без отдельного механизма kill по порогу RSS.

### User Story 5 — Ingest и полнота связей на большом графе (Priority: P1)

Как **потребитель графа**, после анализа крупного прогона я вижу, что
узлы и рёбра code/system записаны согласованно: пакетная обработка
выдерживает объём, инкремент удаляет устаревшее, нет рёбер к
несуществующим узлам в том же снимке прогона.

**Why this priority**: Некорректный ingest при масштабе ломает доверие к
графу сильнее медленного UI.

**Independent Test**: Прогон на fixture с code+system; проверка отсутствия
dangling edges; incremental delete/upsert path.

**Acceptance Scenarios**:

1. **Given** большой envelope/набор узлов, **When** ingest, **Then**
   запись завершается без ошибки OOM/timeout в пределах политики этапа.
2. **Given** инкрементальный прогон с удалёнными путями, **When** ingest,
   **Then** соответствующие узлы/рёбра code и system обновляются или
   удаляются.
3. **Given** cross-parser рёбра (system), **When** цель отсутствует в
   снимке, **Then** ребро **не** сохраняется (как политика `009` FR-010).

---

### User Story 6 — Списки и поиск на большом графе (Priority: P2)

Как **пользователь портала**, на графе с большим числом узлов я открываю
экраны списка/поиска/дерева и получаю страницы результатов без зависания
UI и без счётчиков, противоречащих фильтру слоя.

**Why this priority**: Canvas отложен; списочный UX — единственный способ
проверить граф на масштабе.

**Independent Test**: Проект после анализа large fixture; пагинация корней/
детей и поиск; фильтр слоя согласован с отображаемыми элементами.

**Acceptance Scenarios**:

1. **Given** проект после анализа large-repo (фактический node_count
   ≫ размер страницы; ориентир ≥10 000 не обязателен), **When** загружают
   корни / «ещё» / поиск, **Then** UI отвечает постранично без загрузки
   всего графа в браузер и без таймаута на первую страницу.
2. **Given** фильтр слоя `code` или `system`, **When** смотрят список /
   поиск, **Then** отображаемые элементы и отображаемые счётчики
   согласованы с фильтром (без «пустой страницы» из‑за клиентского
   отсечения без дочитывания).

### User Story 7 — Общий CLI для парсеров (Priority: P3, follow-up)

Как **разработчик парсеров**, после закрытия scale MVP я использую
общий контракт аргументов CLI и записи envelope, чтобы не дублировать
обвязку в каждом модуле.

**Why this priority**: Нужный техдолг, но **не блокирует** SC/FR масштаба
`010`. Закрытие этапа `010` **не** требует реализации US7; спека
**фиксирует**, что работу **MUST** запланировать следом.

**Independent Test**: После появления shared helper — два парсера им
пользуются; контракт manifest/CLI для оркестратора неизменен.

**Acceptance Scenarios**:

1. **Given** follow-up после `010`, **When** внедряют общий helper,
   **Then** argv/envelope соответствуют контракту `005` без смены
   семантики spawn.

---

### Edge Cases

- Репозиторий больше large-repo fixture (внешний эталон): допускается
  более долгий прогон; MUST сохранить предсказуемое завершение
  (успех / partial / failed), не зависание.
- Sync снова стартует во время анализа: действующие правила `005`
  (конфликт / отказ повторного старта) сохраняются.
- Только system-артефакты или только code: пайплайн масштаба MUST
  работать в обоих случаях.
- Пустой change-set (incremental, нет изменений): прогон коротко
  завершается без лишнего тяжёлого парсинга (поведение `005`).
- Парсер исчерпал таймаут: envelope отсутствует или неполный; статус
  failed/partial без порчи предыдущего успешного снимка графа сверх
  политики инкремента/bootstrap.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST выполнять не более одного полного обхода
  дерева рабочей копии на согласованный цикл **sync + подготовка
  анализа**. Типовой путь: sync строит **file inventory** (один walk);
  детектор и change-set MUST читать этот снимок и MUST NOT выполнять
  независимый повторный полный walk того же WC в том же цикле.
- **FR-002**: Система MUST публиковать (в quickstart / отчёте прогона)
  измеримые показатели: длительности sync, детектора, analysis run,
  ingest и counts узлов/рёбер для эталонного large fixture.
- **FR-003**: C#-парсер и оркестратор MUST поддерживать политику таймаута
  и завершение с явным статусом на репозиториях с несколькими
  проектами/solutions.
- **FR-004**: Инкрементальный анализ MUST ограничивать тяжёлую работу
  затронутыми путями (code и system) при наличии валидного предыдущего
  снимка графа. DoD MUST включать **измеримое** сравнение full vs
  incremental (см. SC-003) либо документированную причину недоступности
  инкремента.
- **FR-005**: Оркестратор MUST соблюдать лимит параллельных парсеров и
  политику таймаута; MUST фиксировать результат каждого запланированного
  модуля (success / failed / skipped / missing) с причиной при неуспехе.
  Hard cap RAM на subprocess **не** требуется в MVP `010`.
- **FR-006**: Ingest MUST выполнять пакетную запись узлов/рёбер и
  корректный инкрементальный upsert/delete для code- и system-слоя.
- **FR-007**: Ingest MUST NOT сохранять рёбра, у которых отсутствует
  один из концов в снимке узлов данного прогона (политика already in
  `009` FR-010 / аудит P0 — зафиксировать как требование масштаба).
- **FR-008**: Graph API и списочный UI MUST обеспечивать постраничный
  доступ к узлам/рёбрам и поиск без обязательной загрузки всего графа
  на клиент; при фильтре слоя счётчики и списки MUST быть согласованы.
- **FR-009**: Документация MUST описать **обязательный** ручной smoke на
  внешнем эталоне масштаба оператора **без** коммита эталона в ODS и
  **без** CI; DoD этапа включает зафиксированный результат этого smoke.
- **FR-010**: Общий parser CLI SDK (parseArgs + envelope) **MUST** быть
  зафиксирован как **обязательный follow-up** после scale MVP; **MUST NOT**
  блокировать закрытие FR-001…FR-009 и FR-013. Реализация SDK **не** входит
  в DoD этапа `010`, но **не** считается «отменённой».
- **FR-011**: Изменения MUST NOT требовать правок `specs/009-system-landscape/spec.md`;
  новая семантика system-слоя вне масштаба — вне scope.
- **FR-012**: Canvas / интерактивная схема MUST NOT реализовываться в
  рамках этой фичи.
- **FR-013**: Во время sync и analysis run портал MUST показывать
  оператору **видимый прогресс хода**. На **sync** достаточно текущего
  этапа цикла (например «Синхронизация…») без обязательных счётчиков
  файлов/элементов. При **analysis run** дополнительно — активный
  парсер и/или «N из M» завершённых/запланированных модулей.
  Процентная полоса **не** обязательна в MVP.

### Key Entities

- **File inventory snapshot**: согласованный снимок относительных путей
  и метаданных файлов WC на момент sync/анализа; источник для
  детектора и change-set.
- **Scale run report**: измеренные длительности этапов и counts графа
  для приёмки (fixture + обязательный closing smoke).
- **Run progress indicator**: отображаемый оператору статус хода длительной
  операции (текущий этап sync/анализа).
- **Parser result summary**: статус и сообщение по каждому модулю в
  прогоне (уже есть в `005`; ужесточается для масштаба).
- **Graph page / search result**: страница узлов или рёбер с total/
  offset; согласованность с фильтром слоя.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На large-repo fixture (порядка ≥1000 файлов) полный цикл
  sync → детектор → анализ → ingest завершается предсказуемо (success
  или partial с расшифровкой) за **≤ 15 минут** wall-clock в пилотном
  стеке.
- **SC-002**: Число полных обходов дерева WC за один цикл **sync +
  подготовка анализа** ≤ 1: inventory из sync (или equivalent reuse
  snapshot) обслуживает detector и change-set; **обязательное**
  подтверждение (тест/инструментирование) — на **large-repo** (порядка
  ≥1000 файлов). Отдельный walk sync «сверх» inventory **не**
  допускается как оправдание второго полного обхода. Unit/smoke на
  меньших WC допустимы как регрессия, но **не** закрывают SC-002.
- **SC-003**: Повторный анализ после изменения ≤1% файлов WC завершается
  быстрее полного baseline того же репозитория не менее чем на **40%**
  (по wall-clock analysis+ingest). Закрытие критерия — **обязательный
  замер** на large-repo (или эквиваленте) с записью в quickstart/отчёт
  прогона **или** явная документированная причина, если инкремент
  недоступен (тогда 40% не требуется, но fallback MUST быть записан).
- **SC-004**: После успешного/частичного прогона доля «висячих» рёбер
  (концы без узлов в том же `analysis_run`) = **0%** на контрольных
  проверках fixture.
- **SC-005**: Пользователь открывает дерево узлов и поиск на проекте после
  анализа **large-repo** (на фактическом числе узлов графа этого прогона)
  и получает первую страницу **без** таймаута UI (ощущаемо < 3 с до
  появления первой страницы при работающем backend на пилоте). Цель
  **≥10 000** узлов — желательный ориентир масштаба; если large-repo
  даёт меньше, DoD **не** блокируется — фиксируют фактический
  `node_count` в отчёте/quickstart.
- **SC-006**: Quickstart позволяет оператору за один проход снять таблицу
  длительностей и counts на fixtures; closing smoke на внешнем эталоне
  масштаба выполнен и зафиксирован (успех или `partial` с расшифровкой)
  без изменения git ODS и без CI.
- **SC-007**: Во время прогона ≥ 30 с оператор видит актуальный этап:
  на sync — этап синхронизации; на фазе анализа — активный парсер или
  «N из M», без застывшей «тишины» до завершения.

## Assumptions

- `002`–`009` реализованы и остаются источником функциональной семантики;
  эта фича — hardening/scale поверх них.
- Внешний эталон масштаба — крупный локальный репозиторий оператора
  (вне git ODS); обязателен для DoD этапа (`010`) как **manual** smoke,
  в CI ODS не требуется.
- Существующий fixture `large-repo` / `setup-demo-repos` — базовый
  автоматический эталон; пороги SC уточняются в plan при необходимости.
  Для SC-002 assert walk-count DoD — **large-repo** (≥1000 файлов), не
  мелкий unit alone.
- Canvas (`011-ods-graph-viewer`) начинается **после** закрытия критериев
  этой спеки (или явного решения команды «accept residual risk»).
- US7 (parser CLI SDK) — **обязательный follow-up** после SC-001…SC-007;
  не в DoD `010`, но в roadmap/спеке должно остаться явное «надо сделать».
- Hard RAM cap на парсеры — вне MVP; достаточно timeout + max parallel.
- Язык артефактов спеки и UI — русский (конституция / видение).
