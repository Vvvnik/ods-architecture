# Спецификация: Модель данных MVP

**Фича**: `002-domain-model`

**Создано**: 2026-07-07

**Обновлено**: 2026-07-08

**Статус**: Черновик (инкремент: удаление проекта)

**Вход**: Инкремент post-MVP пилота: операция удаления проекта — снятие
метаданных из Elasticsearch (каскад по дереву), освобождение источника для
повторного импорта; очистка рабочей копии на filesystem для `git_url`.
Источник идей: `ods-help/user-guide/later.md` (п. 1).

**Родительская спека**: `specs/001-ods-vision/spec.md` (этап 1)

**Потребитель**: `specs/003-portal-mvp/spec.md` (этап 2)

## Краткое описание

Backend-слой MVP хранит **проекты** (импортированные репозитории), **дерево
элементов** (файлы и папки рабочей копии) и **статусы** элементов. Метаданные —
JSON в Elasticsearch; содержимое файлов — на диске. Парсеры, граф, RAG и UI
в эту спеку **не входят**.

## Границы спеки

### Входит

- регистрация проекта по Git URL или локальному пути;
- sync рабочей копии и построение дерева;
- чтение содержимого текстовых файлов (read-only);
- смена статуса элемента;
- операции backend для списка проектов, дерева (с пагинацией), sync, статусов;
- **удаление проекта** (метаданные в ES + рабочая копия для `git_url`).

### Не входит

- UI, меню, панели (`003-portal-mvp`);
- языковые парсеры, граф зависимостей;
- RAG, векторный поиск;
- редактирование/удаление файлов на диске через API;
- аутентификация и роли;
- удаление исходников с сохранением только метаданных (post-MVP, `001`);
- UI удаления проекта (`003-portal-mvp`);
- soft-delete проекта с корзиной и восстановлением;
- переименование проекта без удаления (PATCH `name`).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Регистрация проекта (Priority: P1)

Как **разработчик**, я регистрирую репозиторий по Git URL или локальному пути,
чтобы платформа создала проект и начала подготовку рабочей копии.

**Why this priority**: Без сущности «Проект» невозможны импорт и sync.

**Independent Test**: POST регистрации → проект в списке с корректным источником
и статусом операции.

**Acceptance Scenarios**:

1. **Given** валидный Git URL, **When** регистрация, **Then** создаётся проект
   с `source_type` = `git_url`, уникальным `id` и запускается **начальный sync**.
2. **Given** валидный локальный путь, **When** регистрация, **Then** создаётся
   проект с `source_type` = `local_path` и запускается начальный sync.
3. **Given** проект с тем же `source_type` + `source_value` уже существует,
   **When** повторная регистрация, **Then** возвращается существующий проект
   (идемпотентность), новый дубликат **не** создаётся.

---

### User Story 2 — Синхронизация и дерево файлов (Priority: P1)

Как **архитектор**, я запускаю sync и получаю актуальное дерево файлов и папок
с метаданными.

**Why this priority**: Дерево — основа навигации в портале.

**Independent Test**: После успешного sync дерево в хранилище соответствует
рабочей копии на диске (без `.git`).

**Acceptance Scenarios**:

1. **Given** проект зарегистрирован, **When** sync завершён успешно,
   **Then** для каждого файла и папки рабочей копии (кроме `.git`) есть элемент
   с `path`, `type`, `status` = `auto_found`, `is_active` = true.
2. **Given** в рабочей копии новый файл, **When** повторный sync,
   **Then** появляется новый элемент со статусом `auto_found`.
3. **Given** файл удалён из рабочей копии, **When** повторный sync,
   **Then** элемент получает `is_active` = false (soft-delete); запись
   сохраняется для истории статусов.
4. **Given** файл с тем же путём снова появился, **When** sync,
   **Then** элемент реактивируется (`is_active` = true); статус сохраняется,
   если был изменён вручную, иначе `auto_found`.

---

### User Story 3 — Просмотр содержимого файла (Priority: P1)

Как **разработчик**, я запрашиваю содержимое текстового файла по идентификатору
элемента, чтобы отобразить его в портале (read-only).

**Why this priority**: Портал MVP не редактирует файлы, но MUST читать их.

**Independent Test**: Открыть элемент типа `file` → получить текст или признак
«не текстовый» / ошибку кодировки.

**Acceptance Scenarios**:

1. **Given** активный элемент `file` в UTF-8, **When** запрос содержимого,
   **Then** возвращается текст файла из рабочей копии.
2. **Given** бинарный файл, **When** запрос содержимого,
   **Then** возвращается признак `not_text` без тела файла.
3. **Given** элемент `is_active` = false, **When** запрос содержимого,
   **Then** ошибка «файл недоступен» (понятное сообщение на русском).

---

### User Story 4 — Статус элемента (Priority: P2)

Как **архитектор**, я меняю статус файла или папки для фиксации решений по
кодовой базе.

**Independent Test**: PATCH статуса → перечитать элемент → статус сохранён
после перезапуска сервиса.

**Acceptance Scenarios**:

1. **Given** активный элемент, **When** установка статуса из FR-004,
   **Then** статус сохраняется в метаданных элемента.
2. **Given** новый элемент после sync, **When** статус не менялся,
   **Then** `status` = `auto_found`.

---

### User Story 5 — Удаление проекта (Priority: P2)

Как **разработчик**, я удаляю проект из платформы, чтобы убрать битые,
тестовые или устаревшие записи из списка и при необходимости импортировать
тот же источник заново с новым именем.

**Why this priority**: После пилота накопленные проекты в Elasticsearch мешают
демо; полная очистка через `down -v` слишком грубая.

**Independent Test**: DELETE проекта → проект отсутствует в списке; повторная
регистрация того же `(source_type, source_value)` создаёт новый `id` и имя.

**Acceptance Scenarios**:

1. **Given** существующий проект, **When** удаление, **Then** документ проекта
   и **все** элементы дерева с этим `project_id` удалены из хранилища
   метаданных; операция завершается успешно без тела ответа.
2. **Given** проект с `source_type` = `git_url`, **When** удаление,
   **Then** каталог рабочей копии этого проекта на filesystem backend удалён.
3. **Given** проект с `source_type` = `local_path`, **When** удаление,
   **Then** метаданные удалены; исходный каталог на mount/read-only пути
   **не** изменяется.
4. **Given** проект удалён, **When** регистрация с тем же `source_type` и
   `source_value`, **Then** создаётся **новый** проект (новый `id`, новое имя
   из запроса), начальный sync запускается.
5. **Given** другие проекты в хранилище, **When** удаление одного проекта,
   **Then** остальные проекты и их деревья **не** затрагиваются.

---

### Edge Cases

- Неверный URL / недоступный путь: проект в `sync_status` = `failed`,
  `last_error_message` заполнен; повторный sync разрешён.
- Репозиторий > 10 000 файлов: sync в `partial` или `success` с отчётом;
  дерево отдаётся **постранично** (ленивая выборка детей папки).
- Sync уже выполняется: повторный запуск → отказ с понятным сообщением
  (без параллельного sync одного проекта).
- Симлинки: обходятся; битые симлинки — в отчёте sync, не ломают весь sync.
- Пустой репозиторий: проект существует, дерево — корень без дочерних файлов.
- Кодировка не UTF-8: ошибка с кодом `encoding_unsupported` для портала.
- Удаление во время `sync_status` = `running`: отказ с кодом `sync_in_progress`;
  повторить после завершения или прерывания sync.
- Удаление несуществующего проекта: ошибка `not_found`.
- Удаление одного проекта **не** эквивалентно полной очистке хранилища
  (остальные записи и volumes сохраняются).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST хранить **Проект** (`Project`) с полями: `id`, `name`,
  `source_type` (`git_url` | `local_path`), `source_value`, `working_copy_root`
  (внутренний путь на диске), `created_at`, `last_sync_at`, `sync_status`
  (`idle` | `running` | `success` | `failed` | `partial`), `last_error_message`
  (nullable).
- **FR-002**: Регистрация проекта MUST запускать **начальный sync** автоматически.
- **FR-003**: Рабочая копия файлов MUST храниться на **filesystem** отдельно
  от JSON-метаданных в Elasticsearch.
- **FR-004**: Система MUST хранить **элемент дерева** (`ProjectElement`): `id`,
  `project_id`, `path` (относительный от корня репозитория), `parent_path`,
  `type` (`file` | `directory`), `status`, `is_active` (boolean).
- **FR-005**: Допустимые **статусы**: `auto_found`, `needed`, `not_needed`,
  `found`, `unused`. По умолчанию при появлении элемента — `auto_found`.
- **FR-006**: Метаданные `Project` и `ProjectElement` MUST сериализоваться в
  **JSON** и храниться в Elasticsearch (отдельные индексы; имена — в `plan.md`).
- **FR-007**: Sync MUST быть **идемпотентным** по паре `project_id` + `path`:
  повторный sync не создаёт дубликатов активных элементов.
- **FR-008**: Каталог **`.git`** MUST NOT попадать в пользовательское дерево.
- **FR-009**: Запрос дочерних элементов папки MUST поддерживать **пагинацию**
  (limit/offset или cursor); по умолчанию limit ≤ 100.
- **FR-010**: Чтение файла MUST возвращать: текст (UTF-8), `not_text` для
  бинарных, или ошибку кодировки; запись на диск через API MUST NOT быть
  доступна в MVP.
- **FR-011**: Backend MUST предоставлять операции (контракт REST — в `plan.md`):

  | Операция | Назначение |
  |----------|------------|
  | Список проектов | Все импортированные проекты, сортировка по `last_sync_at` ↓ |
  | Получить проект | Метаданные и статус sync |
  | Зарегистрировать проект | Создание + начальный sync |
  | Запустить sync | Обновление рабочей копии и дерева |
  | Дочерние элементы | Дети папки с пагинацией |
  | Получить элемент | Метаданные одного узла |
  | Обновить статус | Смена `status` элемента |
  | Содержимое файла | Read-only текст |
  | Удалить проект | Удаление метаданных проекта и каскад элементов дерева |

- **FR-012**: Сообщения об ошибках API MUST быть на **русском языке** и
  содержать код ошибки для UI (`source_unreachable`, `sync_in_progress`, …).

- **FR-013**: Операция **удаления проекта** MUST:
  - принимать идентификатор существующего проекта;
  - удалять документ проекта из хранилища метаданных;
  - **каскадно** удалять все элементы дерева с тем же `project_id`
    (hard-delete записей, не `is_active` = false);
  - для `git_url` — удалять каталог рабочей копии проекта на filesystem backend;
  - для `local_path` — **не** изменять исходный каталог (только чтение/mount);
  - освобождать пару `(source_type, source_value)` для последующей регистрации
    нового проекта;
  - отклонять запрос при `sync_status` = `running` (код `sync_in_progress`);
  - возвращать успех без тела ответа при удалении существующего проекта;
  - возвращать `not_found`, если проект не существует.

### Key Entities

- **Проект (`Project`)**: Импортированный репозиторий; источник, корень WC,
  статус и ошибка последнего sync.
- **Элемент дерева (`ProjectElement`)**: Узел файловой структуры; путь, тип,
  статус, признак активности.
- **Статус (`ElementStatus`)**: Перечисление FR-005.
- **SyncRun** *(опционально в MVP)*: журнал запусков sync; MAY быть добавлен
  в `plan.md` без изменения scope.

### Связь с хранилищами

| Данные | Хранилище | Примечание |
|--------|-----------|------------|
| Project, ProjectElement | Elasticsearch (JSON) | Индексы в plan; DELETE проекта — hard-delete |
| Содержимое файлов | Filesystem WC | Путь = `working_copy_root` + `path`; для `git_url` WC удаляется с проектом |
| Граф, RAG | — | post-MVP (`004+`) |

## Success Criteria *(mandatory)*

- **SC-001**: Регистрация тестового репозитория (≤ 1000 файлов) и успешный sync
  дают дерево, совпадающее с WC на диске (без `.git`).
- **SC-002**: Смена статуса элемента сохраняется после перезапуска backend.
- **SC-003**: Повторный sync не увеличивает число записей с одним `project_id`
  + `path`.
- **SC-004**: Запрос детей папки с 500+ элементами возвращает первую страницу
  (≤ 100 записей) менее чем за 2 с на пилотном железе (уточнение в plan).
- **SC-005**: Портал (`003`) может выполнить цепочку «список проектов → sync →
  дерево → содержимое файла» только через операции FR-011.
- **SC-006**: Удаление проекта и повторная регистрация того же источника
  создают новый проект с новым идентификатором; в списке нет удалённого проекта
  и его элементов дерева; для `git_url` на диске backend не остаётся каталога
  удалённой рабочей копии.

## Assumptions

- Elasticsearch и backend в одном Docker Compose с пилотом.
- Один инстанс ODS; мультитенантность и auth не требуются в MVP.
- Локальный путь доступен процессу backend (volume или mount хоста).
- Имена индексов ES и JSON-схема документов детализируются в `plan.md`
  (`data-model.md`, `contracts/`).
- Удаление исходников с сохранением метаданных — post-MVP (`001`).
- Удаление проекта — hard-delete метаданных; не путать с soft-delete элементов
  при sync (FR-007, US2).
- Потребитель UI удаления — `003-portal-mvp` (отдельный инкремент спеки `003`).
