# Спецификация: Портал MVP

**Фича**: `003-portal-mvp`

**Создано**: 2026-07-07

**Обновлено**: 2026-07-07

**Статус**: Черновик

**Вход**: Актуализация веб-портала MVP: единое главное меню, импорт и sync
репозиториев, трёхпанельный интерфейс, просмотр файловой структуры и текстовых
файлов (read-only). Все данные — через backend `002-domain-model`.

**Родительская спека**: `specs/001-ods-vision/spec.md` (этап 2)

**Зависимость**: `specs/002-domain-model/spec.md` (блокер; операции FR-011 в `002`)

## Краткое описание

Веб-портал ODS — точка входа пользователя в MVP. Портал **не хранит** метаданные
самостоятельно: вызывает backend из `002` для регистрации проектов, sync,
дерева, чтения файлов и смены статусов. UX-контракт: **одно главное меню**,
**три панели** при работе с проектом, **read-only** просмотр кода.

## Границы спеки

### Входит

- экраны импорта, списка проектов, рабочего места с тремя панелями;
- главное меню и навигация между разделами;
- отображение статуса sync и ошибок с backend;
- ленивая подгрузка дерева (пагинация API `002`);
- смена статуса элемента в правой панели;
- заглушка «Граф зависимостей»;
- деплой фронтенда в составе Docker Compose.

### Не входит

- схема данных, индексы ES, логика sync (`002-domain-model`);
- парсеры, Graphify, граф с данными, RAG;
- редактирование/удаление файлов;
- аутентификация, роли;
- история изменений, настраиваемые панели, мобильная вёрстка;
- боковое TOC документа.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Импорт и список проектов (Priority: P1)

Как **разработчик**, я регистрирую репозиторий по Git URL или локальному пути
и вижу его в списке с актуальным статусом sync.

**Why this priority**: Точка входа; регистрация в `002` сразу запускает начальный sync.

**Independent Test**: Импорт → проект в списке → отображаются `sync_status` и
при ошибке — `last_error_message`.

**Acceptance Scenarios**:

1. **Given** форма импорта, **When** пользователь вводит валидный Git URL
   и подтверждает, **Then** вызывается регистрация проекта (`002` FR-011),
   проект появляется в списке, отображается индикатор sync (`running` → итог).
2. **Given** тот же источник уже зарегистрирован, **When** повторный импорт,
   **Then** открывается существующий проект без дубликата в списке.
3. **Given** sync завершился с ошибкой, **When** пользователь смотрит список
   или карточку проекта, **Then** виден статус `failed`/`partial` и текст
   ошибки на русском.

---

### User Story 2 — Открытие проекта и sync (Priority: P1)

Как **разработчик**, я выбираю проект из списка, открываю рабочее место
и при необходимости запускаю повторный sync.

**Independent Test**: Выбор проекта → трёхпанельный экран → sync → обновлённое дерево.

**Acceptance Scenarios**:

1. **Given** список проектов, **When** пользователь выбирает проект,
   **Then** открывается рабочий экран с тремя панелями (US-3) и активным
   контекстом `project_id`.
2. **Given** проект открыт, **When** пользователь запускает sync из меню,
   **Then** кнопка sync недоступна на время `running`; по завершении —
   успех или сообщение об ошибке.
3. **Given** backend вернул `sync_in_progress`, **When** повторный запуск sync,
   **Then** портал показывает сообщение без падения интерфейса.

---

### User Story 3 — Трёхпанельный просмотр файлов (Priority: P1)

Как **участник команды**, я навигирую по дереву слева, читаю файл в центре
и вижу свойства справа — в одном окне браузера.

**Why this priority**: Ключевой UX-контракт из `001`.

**Independent Test**: Раскрыть папку → открыть `.ts` файл → текст в центре,
путь и статус справа.

**Acceptance Scenarios**:

1. **Given** проект открыт, **When** экран загружен, **Then** три панели:
   **навигация** | **содержимое** | **свойства**.
2. **Given** папка в дереве, **When** раскрытие, **Then** дочерние элементы
   загружаются с пагинацией (не весь репозиторий сразу).
3. **Given** текстовый файл UTF-8, **When** выбор в дереве,
   **Then** содержимое в центральной панели, **без** кнопок сохранения/удаления.
4. **Given** бинарный файл (`not_text` от backend), **When** открытие,
   **Then** сообщение «файл нельзя отобразить как текст».
5. **Given** неподдерживаемая кодировка, **When** открытие,
   **Then** сообщение об ошибке кодировки, не пустой экран.
6. **Given** элемент с `is_active` = false, **When** отображение дерева,
   **Then** элемент **не показывается** в активном дереве (или скрыт по умолчанию).

---

### User Story 4 — Главное меню (Priority: P1)

Как **пользователь**, я выполняю импорт, sync и навигацию только через
единое главное меню.

**Independent Test**: Цепочка импорт → список → проект → sync → файл — без
выхода из портала и без терминала.

**Acceptance Scenarios**:

1. **Given** пользователь в портале, **When** смотрит меню,
   **Then** пункты: **Импорт**; **Проекты**; **Sync**; **Файловая структура**;
   **Граф зависимостей** (заглушка).
2. **Given** пункт «Граф зависимостей», **When** переход,
   **Then** заглушка: «Доступно в этапах 5–7» (`005`–`007`), без данных графа.
3. **Given** MVP, **When** любой сценарий,
   **Then** вход в систему не запрашивается.

---

### User Story 5 — Смена статуса (Priority: P2)

Как **архитектор**, я меняю статус файла или папки в правой панели.

**Independent Test**: Сменить статус → обновить страницу → значение сохранено.

**Acceptance Scenarios**:

1. **Given** активный элемент выбран, **When** пользователь выбирает статус
   из списка (`auto_found`, `needed`, `not_needed`, `found`, `unused`),
   **Then** портал вызывает обновление статуса (`002`) и отображает
   **русскую** метку в UI.
2. **Given** статус изменён, **When** повторное открытие элемента,
   **Then** отображается сохранённый статус.

---

### Edge Cases

- Дерево 10 000+ файлов: раскрытие папок по запросу; пагинация «ещё» при
  превышении limit страницы.
- Потеря связи с backend: баннер/тост «нет связи», кнопка повтора.
- Sync при открытом файле: дерево обновляется; если файл удалён — сообщение
  в центральной панели, контекст проекта сохраняется.
- Пустой репозиторий: дерево с корнем, центральная панель — placeholder.
- Ширина экрана < 1280px: layout MAY деградировать, но остаётся usable
  (детали в plan).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Портал MUST быть **веб-приложением**, все данные — через API
  backend (`002` FR-011); локальное хранение метаданных проекта MUST NOT
  использоваться как источник правды.
- **FR-002**: Портал MUST предоставлять **единое главное меню** (FR-004 US-4).
- **FR-003**: Экран **импорта** MUST принимать Git URL или локальный путь
  (пояснение: путь на сервере backend в пилоте) и вызывать регистрацию проекта.
- **FR-004**: Экран **списка проектов** MUST показывать имя, источник,
  `sync_status`, `last_sync_at`; при ошибке — `last_error_message`.
- **FR-005**: **Sync** MUST быть доступен только для **выбранного** проекта;
  во время `running` повторный запуск MUST быть заблокирован в UI.
- **FR-006**: Рабочий экран проекта MUST иметь **три панели**:
  - левая — дерево файлов (корень репозитория; `.git` не отображается);
  - центральная — просмотр файла read-only или placeholder;
  - правая — путь, тип, статус, действие смены статуса (P2).
- **FR-007**: Дерево MUST загружать детей папки **лениво** с пагинацией API `002`.
- **FR-008**: Просмотр файлов MUST быть **read-only**; кнопки сохранения,
  удаления, создания файлов MUST NOT отображаться.
- **FR-009**: Портал MUST отображать ошибки backend на **русском**,
  используя коды ошибок (`source_unreachable`, `sync_in_progress`,
  `encoding_unsupported`, …) для выбора текста.
- **FR-010**: Пункт «Граф зависимостей» MUST показывать **заглушку** без
  вызова API графа.
- **FR-011**: Портал MUST NOT требовать терминала, входа в систему и
  бокового TOC документа.
- **FR-012**: Состав поставки MUST включать **Docker Compose** с сервисами
  frontend, backend и Elasticsearch (совместно с `002`).

### Соответствие UI и backend (`002`)

| Действие в портале | Операция `002` |
|--------------------|----------------|
| Импорт / регистрация | Зарегистрировать проект |
| Список / карточка проекта | Список проектов / Получить проект |
| Sync | Запустить sync |
| Раскрытие папки | Дочерние элементы |
| Выбор узла | Получить элемент |
| Открытие файла | Содержимое файла |
| Смена статуса | Обновить статус |

### Отображение статусов в UI

| Код (`002`) | Метка в портале |
|-------------|-----------------|
| `auto_found` | Найдено автоматически |
| `needed` | Нужен |
| `not_needed` | Не нужен |
| `found` | Найден |
| `unused` | Не используется |

### Типы панелей

| Панель | MVP | Post-MVP |
|--------|-----|----------|
| Файловая структура | да | — |
| Просмотр файла (read-only) | да | редактирование |
| Свойства / статус | да | — |
| Граф зависимостей | заглушка | да |
| История изменений | нет | да |
| Настройки | нет | да |
| Настраиваемый набор панелей | нет | да |

### Key Entities

Сущности данных — в `002`. На уровне UI:

- **Контекст сессии**: `project_id` (активный проект), `element_id` (выбранный
  узел), `left_panel_mode` (`files` | `graph_stub`).

## Success Criteria *(mandatory)*

- **SC-001**: Пользователь за **5 минут** без терминала: импортирует тестовый
  репозиторий, дожидается sync, открывает `.md` или `.ts` файл и читает содержимое.
- **SC-002**: Все пункты меню (FR-002) ведут на экран или заглушку; нет мёртвых ссылок.
- **SC-003**: При ширине ≥ 1280px три панели видны одновременно на экране проекта.
- **SC-004**: Раскрытие папки с 200+ детьми не блокирует UI (пагинация/подгрузка).
- **SC-005**: Участник пилота подтверждает: базовый просмотр кода — в одном
  интерфейсе (качественная оценка).
- **SC-006**: Выполняется цепочка приёмки `002` SC-005 через только UI портала.

## Assumptions

- Backend и контракт API реализованы по `002` и `plan.md` backend-спеки.
- Фронтенд MVP — TypeScript; стек детализируется в `plan.md` этой фичи.
- Локальный путь в форме импорта — путь, доступный backend на хосте деплоя.
- Мобильная адаптация и drag-and-drop панелей — post-MVP.

## Зависимости

- `specs/001-ods-vision/spec.md` — границы MVP, трёхпанельный UX, read-only.
- `specs/002-domain-model/spec.md` — все операции данных; портал не дублирует FR backend.
