# Спецификация: ODS-платформа — видение и дорожная карта

**Фича**: `001-ods-vision`

**Создано**: 2026-06-26

**Обновлено**: 2026-07-07

**Статус**: Черновик

**Вход**: Актуализация верхнеуровневого видения ODS-платформы с учётом согласованных
дочерних спек `002-domain-model` и `003-portal-mvp`, их планов реализации и
общей инфраструктуры `docker/`. Конституция v1.1.0, пр. VI.

## Цель и ценность

**Проблема:** команда работает с кодом, документацией и знаниями о репозитории
в разрозненных инструментах и терминале.

**Решение:** **ODS-платформа** — единый веб-портал организации, в котором
основные действия по коду и (в перспективе) накопленным знаниям выполняются
в одном интерфейсе без обязательного терминала для конечного пользователя.

**Ключевое отличие:** собственная архитектура и UX ODS; не ориентация на
Backstage и чужие портальные каркасы.

## Краткое описание

**ODS-платформа** — веб-приложение в виде **микросервиса** (фронтенд + backend),
разворачиваемое в **Docker**, которое:

1. импортирует и синхронизирует рабочую копию git-репозитория;
2. хранит структуру и метаданные проекта;
3. в перспективе извлекает знания о коде (парсеры, Graphify, RAG);
4. показывает всё через единый интерфейс с главным меню.

**Архитектурный контур:**

| Компонент | Назначение | MVP | Post-MVP |
|-----------|------------|-----|----------|
| **Фронтенд** | UI, меню, панели, просмотр | да (`003`) | расширение |
| **Backend-сервис** | Логика, sync, REST API, хранилище | да (`002`) | анализ кода |
| **REST API** | Контракт между порталом и backend | да (`002`) | расширение |
| **Elasticsearch** | JSON-метаданные (проект, дерево, статусы) | да (`002`) | граф, RAG |
| **Filesystem** | Рабочая копия файлов репозитория | да (`002`) | политика удаления исходников* |
| **Docker Compose** | Dev/full стек ES + backend + frontend | да (`docker/`) | runtime-спека `004` |
| **Парсеры / Graphify** | Извлечение структуры и графа кода | нет | да (`005+`) |

\* *Политика:* после анализа исходники **MAY** быть удалены с сохранением
извлечённых метаданных — зафиксировано в видении, реализация post-MVP.

**MVP (этапы 1–2)** — импорт репозитория, sync, единое главное меню,
трёхпанельный интерфейс, просмотр файловой структуры и текстовых файлов
(read-only). Детальные требования и сценарии — **только** в `002` и `003`.

**Полное видение (post-MVP)** — два **независимых канала** накопления знаний
о коде:

1. **Языковые парсеры** (Roslyn, TypeScript AST и др.) — backend определяет
   языки проекта и строит единый граф зависимостей.
2. **Graphify** — отдельный инструмент со **своим форматом данных**, в составе
   ODS; платформа оркестрирует запуск и показывает результаты в UI.

Дополнительно: RAG/Q&A, документация AsciiDoc/PDF, аутентификация, агенты
и интеграции (MCP, Cursor).

## Пользователи

- **MVP:** внутренние команды разработки и архитектуры (пилот); общий доступ
  без входа; одинаковые права.
- **Post-MVP:** роли «читатель» / «редактор»; внешние пользователи — отдельное
  решение.

## Границы MVP

### Входит в MVP

| Область | Содержание | Спецификация | План |
|---------|------------|--------------|------|
| Модель данных | Проект, дерево, статусы, JSON в ES, REST API | `002-domain-model` | ✅ |
| Портал | Меню, импорт, sync, список проектов, 3 панели, read-only | `003-portal-mvp` | ✅ |
| Контракт API | Канон OpenAPI в `002`; зеркало потребителя в `003` | `002` / `003` | ✅ |
| Деплой (dev) | `docker/docker-compose.dev.yml`: ES; профиль `full` — backend + frontend | `docker/` | ✅ |
| Доступ | Без входа (внутренний пилот) | `002`, `003` | — |

### Не входит в MVP

**Анализ и знания о коде**

- определение языков и подключение парсеров / анализаторов (Roslyn, TS AST);
- построение и просмотр графа зависимостей (в меню — **заглушка**);
- Graphify и оркестрация анализа;
- RAG и векторный поиск;
- удаление исходников с сохранением только метаданных.

**Портал и платформа**

- редактирование и удаление файлов в UI;
- история изменений рабочей копии;
- настраиваемый набор панелей на рабочем столе;
- вход, учётные записи, роли;
- Git push/merge из UI;
- раздел «Документация», ручные связи документ ↔ код;
- PDF, AsciiDoc pipeline, импорт legacy Wiki;
- Q&A, агенты, Telegram, интеграция с Cursor.

## Карта дочерних спек MVP

Краткая сводка без дублирования FR (детали — в дочерних `spec.md`).

### `002-domain-model` (этап 1, backend)

- Регистрация проекта по Git URL или локальному пути; **начальный sync** при создании.
- Асинхронный sync; soft-delete элементов (`is_active` = false).
- Дерево файлов/папок с пагинацией; `.git` не в пользовательском дереве.
- Read-only чтение текстовых файлов; смена статуса элемента.
- Метаданные в Elasticsearch; содержимое — на filesystem.
- REST API `/api/v1` — канон в `plan.md` → `contracts/openapi.yaml`.

### `003-portal-mvp` (этап 2, frontend)

- Единое главное меню: Импорт, Проекты, Sync, Файловая структура, Граф (заглушка).
- Три панели: дерево | просмотр файла | свойства/статус.
- Все данные через API `002`; русские метки статусов и ошибок.
- Polling статуса sync; блокировка повторного sync при `running`.
- Деплой frontend в составе `docker/` (профиль `full`, порт портала 8080).

### `docker/` (инфраструктура MVP)

- Общий compose для `002` и `003`; не отдельная продуктовая спека.
- Профиль по умолчанию: только Elasticsearch (локальная разработка).
- Профиль `full`: elasticsearch + backend + frontend (nginx, proxy `/api`).
- Детали — в `003/contracts/docker-integration.md` и `quickstart.md` обеих спек.

## Дорожная карта по этапам

| Этап | Фокус | Спецификация | Статус |
|------|-------|--------------|--------|
| 0 | Видение, границы, карта спек | `001-ods-vision` | этот документ |
| 1 | Модель данных MVP, backend API | `002-domain-model` | spec + plan |
| 2 | Портал MVP: меню, импорт, sync, UI | `003-portal-mvp` | spec + plan |
| 3 | Runtime MVP: полный compose, smoke, фикстуры | `004-mvp-runtime` | планируется |
| 4 | Анализ кода: парсеры, адаптеры | `005-code-analysis` | планируется |
| 5 | Граф: импорт, обновление, версии | `006-project-graph` | планируется |
| 6 | Интеграция Graphify в составе ODS | `007-graphify-integration` | планируется |
| 7 | Документация AsciiDoc, PDF | `008-documentation` | планируется |
| 8 | RAG, MCP, внешние агенты | `009-rag-mcp` | планируется |
| 9 | Аутентификация и роли | `010-auth` | планируется |

**Порядок реализации MVP:**

```
001 (согласование) → 002 (backend) → 003 (портал) → plan/tasks → код
                              ↘ docker/ (dev/full compose)
```

`002` — **блокер** для `003`. Этап `004-mvp-runtime` формализует приёмку
полного стека (smoke, фикстурные репо); до его появления пилотный compose
описан в `docker/` и планах `002`/`003`.

Планирование и задачи: `/speckit-plan` и `/speckit-tasks` выполнены для `002` и `003`.
Следующий шаг — `/speckit-implement`.

## Критерии успеха видения

Проверяются на уровне этапа 0; числовые пороги производительности — в дочерних
спеках (`002` SC-001–SC-005, `003` SC-001–SC-006).

- **SC-V01**: Дорожная карта покрывает MVP и все заявленные направления
  post-MVP (парсеры, Graphify, граф, RAG, документация, auth).
- **SC-V02**: Границы MVP однозначны: любая фича из списка «не входит» не
  появляется в `002`/`003` без обновления этого документа.
- **SC-V03**: Дочерние спеки `002` и `003` ссылаются на `001`, имеют согласованные
  `plan.md`, `tasks.md` и не дублируют разделы видения.
- **SC-V04**: После реализации MVP участник пилота подтверждает: импорт
  репозитория и просмотр текстового файла доступны в одном веб-интерфейсе
  без терминала (приёмка `003` SC-001, SC-005, SC-006).

## Сквозные решения

- **Стек MVP:** TypeScript (фронтенд и backend); деплой через Docker Compose
  в каталоге `docker/`. Backend на .NET — post-MVP или отдельное решение в `001`.
- **Формат метаданных:** JSON в Elasticsearch; схема и индексы — в `002` (`plan.md`,
  `data-model.md`, `contracts/`).
- **Контракт API:** канон — `002/contracts/openapi.yaml`; портал потребляет тот же
  контракт (зеркало в `003/contracts/api-consumer.yaml`).
- **Источник проекта:** Git URL или локальный путь к папке с git-репозиторием
  (путь доступен процессу backend на хосте деплоя).
- **Язык UI и артефактов:** русский.
- **Иерархия спек:** `001` — только видение; FR и user stories — в `00N-*`
  начиная с `002` (конституция, пр. VI).

## Принятые решения

- Одна **главная спека** (`001`) — видение и карта; **детализация** — в дочерних.
- **MVP = `002` + `003`**, не монолитный документ; инфраструктура compose — `docker/`.
- Файлы в MVP — **только просмотр**; редактирование — следующая итерация портала.
- Пункт «Граф зависимостей» в меню MAY быть виден с **заглушкой** (данные — этапы 5–7).
- Боковое оглавление (TOC) в MVP **не делаем**.
- Не подстраиваемся под Backstage и его структуру.
- Sync **асинхронный**; повторный запуск одного проекта во время `running` — отказ.

## Assumptions

- Пилот разворачивается как один инстанс для внутренней команды.
- Локальный путь при импорте доступен процессу backend (volume/mount хоста).
- Черновики `ods-help/requirements/` — источник идей, не замена `specs/**`.
- Этап `004-mvp-runtime` не блокирует первую реализацию кода; compose в `docker/`
  достаточен для разработки и пилота до формализации `004`.
