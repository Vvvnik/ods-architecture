# Спецификация фичи: ODS-платформа — видение и границы MVP

**Ветка фичи**: `001-ods-vision`

**Создано**: 2026-06-26

**Статус**: Черновик

**Вход**: На основе `ods-help/text.md` (раздел «Видение проекта» и Этап 0): цель,
возможности и границы MVP единой ODS-платформы для работы с исходным кодом,
документацией и знаниями о проекте.

**Версия спецификации**: 1.0.0

## Краткое описание

**ODS-платформа** — единый веб-портал организации (без обязательного использования
терминала конечным пользователем), который объединяет просмотр исходного кода,
накопленные знания о проекте, документацию и в перспективе — помощь ИИ-агентов
при доработке систем. Платформа **не копирует** структуру Backstage; архитектура
и UX определяются собственными спецификациями ODS.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Просмотр проекта как файлового дерева (Priority: P1)

Как **разработчик или архитектор**, я открываю зарегистрированный проект в
ODS-платформе и вижу его файловую структуру, чтобы быстро ориентироваться в
кодовой базе без переключения между разрозненными инструментами.

**Why this priority**: Базовая ценность платформы; без навигации по проекту
остальные возможности не имеют точки входа.

**Independent Test**: Можно зарегистрировать тестовый проект, открыть дерево
файлов и перейти к любому текстовому файлу — без анализа графов и без ИИ.

**Acceptance Scenarios**:

1. **Given** проект добавлен в платформу, **When** пользователь открывает проект,
   **Then** отображается иерархия папок и файлов.
2. **Given** пользователь выбрал текстовый файл, **When** файл открывается,
   **Then** содержимое доступно для чтения в интерфейсе платформы.
3. **Given** пользователь редактирует файл, **When** сохраняет изменения,
   **Then** обновлённое содержимое сохраняется и доступно при повторном открытии.

---

### User Story 2 — Единый интерфейс вместо нескольких порталов (Priority: P1)

Как **участник команды**, я выполняю основные задачи по коду и документации
в одном веб-интерфейсе ODS, чтобы не переключаться между двумя-тремя
отдельными порталами.

**Why this priority**: Ключевое продуктовое отличие из видения (п. 18–19);
определяет целевой UX всей платформы.

**Independent Test**: Пользователь выполняет цепочку «открыть проект → просмотреть
файл → открыть связанный документ» без выхода в терминал и без смены приложения.

**Acceptance Scenarios**:

1. **Given** пользователь авторизован в платформе, **When** работает с проектом,
   **Then** навигация (меню, оглавление) доступна в едином оформлении портала.
2. **Given** пользователь завершил сессию работы с кодом, **When** переходит
   к разделу документации того же проекта, **Then** контекст проекта сохраняется.

---

### User Story 3 — Управление статусом элементов проекта (Priority: P2)

Как **архитектор**, я помечаю файлы и другие элементы проекта статусами
(например: «нужен», «не нужен», «найден», «не используется»), чтобы вести
реестр решений по кодовой базе; по умолчанию новые элементы имеют статус
«найдено автоматически».

**Why this priority**: Заложено в видении (п. 6); даёт ценность до появления
графов и RAG.

**Independent Test**: Пользователь меняет статус элемента и видит его в списке
фильтрации без запуска фонового анализа.

**Acceptance Scenarios**:

1. **Given** элемент обнаружен при импорте или сканировании, **When** он
   появляется в интерфейсе, **Then** статус по умолчанию — «найдено автоматически».
2. **Given** пользователь с правами редактирования, **When** меняет статус,
   **Then** новый статус сохраняется и отображается при следующем открытии.

---

### User Story 4 — Вопросы о проекте с ответом в удобном виде (Priority: P3, post-MVP)

Как **разработчик**, я задаю вопрос о проекте («где добавить функцию X?») через
интерфейс платформы и получаю ответ с указанием релевантных файлов и пояснением
в читаемом виде (текст + при необходимости визуализация связей), а не сырой
вывод внешнего инструмента.

**Why this priority**: Важная долгосрочная цель (п. 5, 10–11), но зависит от
импорта графа и базы знаний — вне MVP.

**Independent Test**: Выполняется после реализации импорта и поиска; в MVP
не тестируется.

**Acceptance Scenarios**:

1. **Given** проект проиндексирован, **When** пользователь задаёт вопрос,
   **Then** ответ содержит список файлов/папок для правки и текстовое пояснение.
2. **Given** ответ включает граф зависимостей, **When** пользователь просматривает
   результат, **Then** граф отображается в интерфейсе платформы, а не только
   в консоли.

### Edge Cases

- Проект с очень большим деревом файлов (десятки тысяч узлов): навигация
  остаётся отзывчивой за счёт ленивой подгрузки или пагинации.
- Файл в неподдерживаемой кодировке: пользователь видит понятное сообщение,
  а не пустой экран.
- Одновременное редактирование одного файла двумя пользователями: система
  предупреждает о конфликте или показывает актуальную версию.
- Импорт прерван или завершился с ошибкой: пользователь видит статус операции
  и может повторить импорт.
- Legacy-страницы Wiki при импорте: сохраняется исходное содержимое;
  формат отображения уточняется на этапе документации (post-MVP).

## Границы MVP

### Входит в MVP

| Область | Содержание |
|---------|------------|
| Цель | Единый портал ODS для просмотра и базовой работы с исходным кодом проекта |
| Навигация | Дерево файлов, открытие и просмотр текстовых файлов |
| Редактирование | Создание и правка текстовых файлов в интерфейсе |
| UX | Единый веб-интерфейс с навигацией и оглавлением; без терминала для пользователя |
| Статусы | Ручная разметка элементов статусами; значение по умолчанию «найдено автоматически» |
| Документация | Подготовка к AsciiDoc (хранение и открытие текстовых документов); полная сборка PDF — post-MVP |

### Не входит в MVP (последующие этапы)

- Импорт и анализ кода через внешние анализаторы (Roslyn, TypeScript AST и др.)
- Построение и хранение графа проекта в структурной БД
- Интеграция Graphify и визуализация графа в UI
- RAG и векторный поиск
- ИИ-агенты, Telegram-бот и подсказки «какие файлы править»
- Интеграция с Git (push, merge) внутри платформы
- Визуальный редактор PDF-стилей и генерация PDF
- Импорт legacy Wiki (Миртех и др.)
- Составление ТЗ в платформе с экспортом в Cursor (post-MVP)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Платформа MUST позволять регистрировать проект и отображать его
  файловую структуру в виде иерархического дерева.
- **FR-002**: Пользователь MUST иметь возможность открывать и читать текстовые
  файлы проекта в интерфейсе платформы.
- **FR-003**: Пользователь MUST иметь возможность создавать, редактировать
  и сохранять текстовые файлы в рамках зарегистрированного проекта.
- **FR-004**: Платформа MUST предоставлять единую навигацию (меню, оглавление)
  для работы с проектом без переключения на отдельные порталы.
- **FR-005**: Каждый учитываемый элемент проекта MUST иметь статус; по умолчанию
  — «найдено автоматически»; пользователь MUST иметь возможность изменить статус
  вручную из предопределённого набора.
- **FR-006**: Платформа MUST NOT требовать от конечного пользователя терминала
  для сценариев MVP (просмотр, редактирование, навигация).
- **FR-007**: Платформа MUST хранить структурные метаданные проекта (дерево,
  статусы, ссылки на содержимое) отдельно от сырых файлов на диске.
- **FR-008**: Система MUST показывать понятные сообщения при ошибках доступа
  к файлу, импорта или сохранения.
- **FR-009** *(post-MVP)*: Платформа MUST импортировать проект во внутренний
  формат с извлечением структуры и зависимостей для последующего анализа.
- **FR-010** *(post-MVP)*: Пользователь MUST иметь возможность задавать вопросы
  о проекте и получать ответы с указанием релевантных файлов в интерфейсе.
- **FR-011** *(post-MVP)*: Платформа MUST поддерживать полнотекстовый и
  семантический поиск по накопленным знаниям о проекте.
- **FR-012** *(post-MVP)*: Документация MUST собираться из AsciiDoc с include
  фрагментов; PDF — по шаблонам ODS через визуальный редактор стилей.

### Key Entities

- **Проект**: Зарегистрированная кодовая база или её представление в платформе;
  имеет имя, корневой путь, метаданные.
- **Элемент проекта**: Файл или папка в дереве; путь, тип, статус, ссылка на содержимое.
- **Статус элемента**: Значение из набора (как минимум: найдено автоматически,
  нужен, не нужен, найден, не используется).
- **Документ**: Текстовый или структурированный материал, привязанный к проекту
  (в перспективе — AsciiDoc).
- **Сессия работы**: Контекст пользователя (активный проект, открытые файлы).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь находит заданный файл в проекте до 50 000 файлов
  не более чем за 30 секунд с момента открытия проекта.
- **SC-002**: 90 % участников пилотной группы выполняют сценарий «открыть проект
  → просмотреть файл → сохранить правку» с первой попытки без обращения к терминалу.
- **SC-003**: Не менее 80 % опрошенных пользователей согласны, что «всё необходимое
  для базовой работы с кодом доступно в одном интерфейсе» (шкала согласия).
- **SC-004**: Время отклика интерфейса при раскрытии папки в дереве — не более
  2 секунд для 95 % операций в пилотных проектах.
- **SC-005** *(критерий готовности видения, не MVP)*: После реализации post-MVP
  модулей 80 % вопросов о месте правки кода получают ответ с указанием файлов
  без ручного поиска по репозиторию.

## Assumptions

- Целевые пользователи — внутренние команды разработки и архитектуры ODS;
  внешние анонимные пользователи в MVP не рассматриваются.
- Аутентификация и разграничение прав будут определены на этапе планирования;
  для MVP достаточно ролей «читатель» и «редактор» внутри организации.
- Технические предпочтения из видения (PostgreSQL для структуры, ChromaDB для
  векторов, Roslyn/TypeScript AST, Graphify) относятся к последующим этапам
  и фиксируются в отдельных спецификациях (001-domain-model, 002-code-analysis и др.).
- Git-операции в MVP выполняются вне платформы (например, в Cursor); интеграция
  с Git — отдельная фича.
- Спецификации и ТЗ для разработки ведутся в репозитории `ods-architecture`
  по SDD-циклу Spec Kit; эта спецификация — Этап 0 (`000-vision` / `001-ods-vision`).
- Язык интерфейса и документов для пользователей ODS — русский, если не оговорено иное.
