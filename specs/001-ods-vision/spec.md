  без ролей «администратор».)*

- Q: Откуда дерево файлов и статус «найдено автоматически» в MVP? → A: При **sync** рабочей копии платформа сканирует файлы/папки, строит дерево и присваивает каждому элементу статус «найдено автоматически».

- Q: Одновременное редактирование одного файла в MVP? → A: При сохранении — **предупреждение о конфликте**, если файл изменился с момента открытия; пользователь перезаписывает или отменяет.

## Краткое описание

**ODS-платформа** — единый веб-портал организации (без обязательного использования
терминала конечным пользователем), который объединяет просмотр исходного кода,
накопленные знания о проекте и документацию. Платформа **не копирует** структуру Backstage; архитектура
и UX определяются собственными спецификациями ODS.

**Полное видение** предполагает два независимых канала накопления знаний о коде:
(1) анализ через языковые парсеры с построением единого графа зависимостей;
(2) **Graphify** — отдельный по логике инструмент со **своим форматом данных**,
поставляемый **в составе ODS** (пользователь не устанавливает его отдельно);
платформа оркестрирует запуск и показывает результаты в интерфейсе. Накопление
графа и Graphify — **post-MVP**; единое хранилище платформы — **Elasticsearch**
(см. Assumptions). Текущий MVP портала — навигация, редактирование и разметка проекта.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Просмотр проекта как файлового дерева (Priority: P1)

Как **разработчик или архитектор**, я открываю зарегистрированный проект в
ODS-платформе и вижу его файловую структуру, чтобы быстро ориентироваться в
кодовой базе без переключения между разрозненными инструментами.

**Why this priority**: Базовая ценность платформы; без навигации по проекту
остальные возможности не имеют точки входа.

**Independent Test**: Можно зарегистрировать тестовый проект, открыть дерево
файлов и перейти к любому текстовому файлу — без анализа графов.

**Acceptance Scenarios**:

1. **Given** проект зарегистрирован через экран регистрации (локальный путь или Git URL),
   **When** пользователь открывает проект, **Then** отображается иерархия папок
   и файлов из рабочей копии платформы.
2. **Given** пользователь выбрал текстовый файл, **When** файл открывается,
   **Then** содержимое доступно для чтения в интерфейсе платформы.
3. **Given** пользователь редактирует файл, **When** сохраняет изменения,
   **Then** обновлённое содержимое сохраняется и доступно при повторном открытии.

---

### User Story 2 — Единый интерфейс вместо нескольких порталов (Priority: P1)

Как **участник команды**, я выполняю основные задачи по коду и документации
в одном веб-интерфейсе ODS, чтобы не переключаться между двумя-тремя
отдельными порталами.

**Why this priority**: Ключевое продуктовое отличие из видения; определяет
целевой UX всей платформы.

**Independent Test**: Пользователь выполняет цепочку «открыть проект → просмотреть
файл → открыть связанный документ» без выхода в терминал и без смены приложения.

**Acceptance Scenarios**:

1. **Given** пользователь открыл платформу (без входа в MVP), **When** работает
   с проектом, **Then** навигация (меню, оглавление) доступна в едином оформлении
   портала.
2. **Given** пользователь завершил просмотр файла кода, **When** переходит
   в раздел «Документация» или открывает связанный документ, **Then** контекст
   проекта сохраняется и документ доступен в том же интерфейсе.
3. **Given** к файлу кода вручную привязан документ, **When** пользователь
   открывает этот файл, **Then** платформа предлагает перейти к связанному
   документу без поиска по дереву.

---

### User Story 3 — Управление статусом элементов проекта (Priority: P2)

Как **архитектор**, я помечаю файлы и другие элементы проекта статусами
(например: «нужен», «не нужен», «найден», «не используется»), чтобы вести
реестр решений по кодовой базе; по умолчанию новые элементы имеют статус
«найдено автоматически».

**Why this priority**: Даёт ценность до появления графов и Graphify.

**Independent Test**: Пользователь меняет статус элемента и видит его в списке
фильтрации без запуска фонового анализа.

**Acceptance Scenarios**:

1. **Given** проект синхронизирован из локального пути или Git URL, **When** элемент
   появляется в дереве, **Then** статус по умолчанию — «найдено автоматически».
2. **Given** пользователь открыл элемент в дереве, **When** меняет статус,
   **Then** новый статус сохраняется и отображается при следующем открытии.

---

### User Story 4 — Просмотр графа зависимостей проекта (Priority: P3, post-MVP)

Как **архитектор**, я открываю зарегистрированный репозиторий и просматриваю
граф сущностей и связей кода, чтобы понимать зависимости без ручного обхода
файлов.

**Why this priority**: Следующий слой ценности после MVP портала; опирается на
подсистему анализа кода (этапы 2–3).

**Independent Test**: После импорта репозитория пользователь выбирает проект,
открывает граф и переходит от узла к связанным сущностям — без терминала.

**Acceptance Scenarios**:

1. **Given** репозиторий импортирован и граф построен, **When** пользователь
   открывает представление графа, **Then** отображаются узлы и связи выбранного
   проекта.
2. **Given** пользователь выбрал узел на графе, **When** запрашивает связанные
   сущности, **Then** платформа показывает навигацию по зависимостям в том же
   интерфейсе.

### Edge Cases

- Проект с очень большим деревом файлов (десятки тысяч узлов): навигация
  остаётся отзывчивой за счёт ленивой подгрузки или пагинации.
- Файл в неподдерживаемой кодировке: пользователь видит понятное сообщение,
  а не пустой экран.
- Одновременное редактирование одного файла: при сохранении, если содержимое
  на диске изменилось с момента открытия, платформа **предупреждает о конфликте**
  и предлагает перезаписать или отменить сохранение (без автоматического merge).
- Импорт или анализ прерван или завершился с ошибкой: пользователь видит статус
  операции и может повторить.
- Graphify недоступен или вернул ошибку: платформа сообщает о сбое анализа,
  остальной функционал портала остаётся доступным.
- Legacy-страницы Wiki при импорте: сохраняется исходное содержимое;
  формат отображения уточняется на этапе документации (post-MVP).

## Границы MVP

### Входит в MVP (портал, этап 0)

| Область | Содержание |
|---------|------------|
| Цель | Единый портал ODS для просмотра и базовой работы с исходным кодом проекта |
| Регистрация проекта | Любой пользователь MVP через экран регистрации задаёт локальный путь или Git URL; платформа синхронизирует рабочую копию (без push/merge); вход и роли не требуются |
| Дерево и статусы | При sync строится дерево файлов/папок; каждому элементу — «найдено автоматически» |
| Навигация | Дерево файлов, открытие и просмотр текстовых файлов |
| Редактирование | Создание и правка текстовых файлов в интерфейсе |
| UX | Единый веб-интерфейс с навигацией и оглавлением; без терминала для пользователя |
| Доступ | Общий доступ **без входа** (внутренний пилот); аутентификация и роли — post-MVP |
| Статусы | Ручная разметка элементов статусами; значение по умолчанию «найдено автоматически» |
| Документация | Текстовые файлы в дереве **и** раздел «Документация»; ручные связи документ ↔ код; сборка PDF — post-MVP |

### Не входит в MVP (последующие этапы)

**Анализ кода и знания о репозитории**

- синхронизация репозиториев для **анализа кода** и инкрементальный пересчёт графа;
- построение единого графа зависимостей (языковые парсеры);
- **Graphify** — отдельный канал извлечения знаний, поставляемый в составе ODS,
  со своим форматом данных; визуализация через интерфейс платформы;
- хранение и навигация по графу кода в Elasticsearch (этапы 2–3, 6);

**Платформа и документация**

- вход в систему, учётные записи и роли «читатель» / «редактор»;
- интеграция с Git (push, merge) внутри платформы;
- визуальный редактор PDF-стилей и генерация PDF;
- импорт legacy Wiki (Миртех и др.);
- составление ТЗ в платформе с экспортом в Cursor.

## Requirements *(mandatory)*

### Functional Requirements

**MVP портала**

- **FR-001**: Пользователь MVP MUST иметь возможность зарегистрировать проект по
  **локальному пути** или **Git URL** через экран регистрации проекта; в MVP
  MUST NOT применяться вход в систему и разграничение ролей для этой операции.
  Платформа MUST синхронизировать рабочую копию, построить дерево файлов и
  папок и отобразить его в иерархическом виде.
- **FR-002**: Пользователь MUST иметь возможность открывать и читать текстовые
  файлы проекта в интерфейсе платформы.
- **FR-003**: Пользователь MUST иметь возможность создавать, редактировать
  и сохранять текстовые файлы в рамках зарегистрированного проекта.
- **FR-004**: Платформа MUST предоставлять единую навигацию (меню, оглавление)
  для работы с проектом без переключения на отдельные порталы.
- **FR-005**: Каждый элемент дерева проекта MUST иметь статус; при появлении
  элемента при sync рабочей копии по умолчанию — «найдено автоматически»;
  любой пользователь MVP MUST иметь возможность изменить статус вручную
  из предопределённого набора.
- **FR-006**: Платформа MUST NOT требовать от конечного пользователя терминала
  и **входа в систему** для сценариев MVP (просмотр, редактирование, навигация).
- **FR-007**: Платформа MUST хранить структурные метаданные проекта (дерево,
  статусы, ссылки на содержимое) отдельно от сырых файлов на диске.
- **FR-008**: Система MUST показывать понятные сообщения при ошибках доступа
  к файлу, импорта или сохранения.
- **FR-009**: Платформа MUST предоставлять раздел **«Документация»** в едином
  интерфейсе; документы MUST быть текстовыми файлами из рабочей копии проекта
  (в т.ч. `.md`, `.adoc`, `.txt`) и открываться тем же просмотрщиком, что и код.
- **FR-010**: Пользователь MUST иметь возможность **вручную связать** документ
  с файлом или папкой кода; платформа MUST сохранять связь в метаданных и
  обеспечивать переход между связанными элементами в UI.
- **FR-011**: При сохранении файла, если его содержимое изменилось на диске
  с момента открытия в текущей сессии, платформа MUST показать предупреждение
  о конфликте и MUST NOT перезаписывать файл без явного подтверждения пользователя.

**Post-MVP (видение платформы)**

- **FR-012** *(post-MVP)*: Платформа MUST импортировать репозиторий и извлекать
  структуру и зависимости кода через канал языкового анализа для построения
  единого графа проекта.
- **FR-013** *(post-MVP)*: Платформа MUST включать Graphify **в состав поставки
  ODS**, оркестрировать его запуск, принимать **собственный формат данных**
  Graphify (отличный от результата языковых парсеров) и отображать результаты
  в интерфейсе без обязательного использования терминала.
- **FR-015** *(post-MVP)*: Пользователь MUST иметь возможность просматривать
  граф зависимостей проекта и навигировать по связям между сущностями кода.
- **FR-017** *(post-MVP)*: Документация MUST собираться из AsciiDoc с include
  фрагментов; PDF — по шаблонам ODS через визуальный редактор стилей.
- **FR-018** *(post-MVP)*: Платформа MUST поддерживать аутентификацию и разграничение
  ролей (как минимум «читатель» и «редактор»).

*Сняты в v1.5.0:* **FR-014** (Q&A о проекте), **FR-016** (семантический/полнотекстовый
поиск по накопленным знаниям), **SC-005**; этап `008-rag` — вне scope.

### Key Entities

- **Проект**: Зарегистрированная кодовая база в платформе; имеет имя, источник
  (локальный путь или Git URL), рабочую копию, метаданные.
- **Элемент проекта**: Файл или папка в дереве; путь, тип, статус, ссылка на содержимое.
- **Статус элемента**: Значение из набора (как минимум: найдено автоматически,
  нужен, не нужен, найден, не используется).
- **Документ**: Текстовый файл проекта (из рабочей копии), доступный в дереве
  и в разделе «Документация»; в перспективе — AsciiDoc с include и PDF.
- **Связь документ ↔ код** *(MVP)*: Ручная привязка документа к файлу или папке
  кода; хранится в метаданных платформы.
- **Репозиторий** *(post-MVP)*: Источник кода (URL или локальный путь);
  синхронизируется в рабочую копию для анализа.
- **Граф проекта** *(post-MVP)*: Узлы и связи сущностей кода; единое представление
  для навигации по графу независимо от канала извлечения.
- **Результат Graphify** *(post-MVP)*: Данные анализа в формате Graphify;
  преобразуются платформой для UI и хранения, не смешиваются с сырым AST.
- **Сессия работы**: Контекст пользователя (активный проект, открытые файлы).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь находит заданный файл в проекте до 50 000 файлов
  не более чем за 30 секунд с момента открытия проекта.
- **SC-002**: 90 % участников пилотной группы выполняют сценарий «открыть проект
  → просмотреть файл → сохранить правку» с первой попытки без обращения к терминалу.
- **SC-003**: Не менее 80 % опрошенных пользователей согласны, что «всё необходимое
  для базовой работы с кодом доступно в одном интерфейсе» (шкала согласия).
- **SC-004**: Время отклика интерфейса при раскрытии папки в дереве — не более
  2 секунд для 95 % операций в пилотных проектах.
- **SC-006** *(post-MVP)*: Пользователь находит связанную сущность на графе
  зависимостей не более чем за 3 перехода от выбранного начального узла
  в типовом модуле пилотного проекта.

## Assumptions

- Целевые пользователи — внутренние команды разработки и архитектуры ODS;
  внешние анонимные пользователи в MVP не рассматриваются.
- **MVP портала — без входа:** общий доступ для внутреннего пилота; все участники
  имеют одинаковые права на просмотр, редактирование и смену статусов. Аутентификация
  и роли «читатель» / «редактор» — post-MVP (FR-018).
- **Документы в MVP:** текстовые файлы в дереве + раздел «Документация»; опциональные
  ручные связи документ ↔ код (FR-009, FR-010). Автоматическое обнаружение связей — post-MVP.
- **MVP портала** и **подсистема анализа кода** — разные срезы зрелости:
  дерево файлов и статусы реализуются первыми; граф и Graphify — по дорожной
  карте этапов 2–6.
- Graphify логически отделён от языковых парсеров (свой формат данных), но
  **физически входит в поставку ODS**; отдельная установка Graphify конечным
  пользователем не предполагается.
- **Хранилище платформы ODS — только Elasticsearch:** метаданные портала (дерево,
  статусы, связи документ ↔ код, задания sync) и граф кода (узлы/рёбра/файлы).
  **PostgreSQL, ChromaDB, векторные индексы, RAG и эмбеддинги не используются.**
  Содержимое файлов проекта хранится на filesystem рабочей копии, не в ES.
- Регистрация проекта в MVP: локальный путь или Git URL → sync → рабочая копия
  и дерево файлов; новые элементы при sync получают статус «найдено автоматически».
  Push, merge и прочие Git-операции в UI — post-MVP (сейчас — вне платформы,
  например в Cursor).
- Спецификации ведутся в репозитории `ods-architecture` по SDD-циклу Spec Kit;
  исходные требования — `ods-help/requirements/`.
- Язык интерфейса и документов для пользователей ODS — русский, если не оговорено иное.
