# Конституция ods-architecture

## Основные принципы

### I. Точечные изменения спецификаций

Изменяется **только** тот артефакт в `specs/NNN-*/`, которого касается правка:
`spec.md`, `plan.md` или `tasks.md`. Запрещено смешивать несвязанные изменения
в одном файле или одном коммите без явного обоснования.

*Обоснование:* снижает риск регрессий и упрощает согласование и откат.

### II. Версионирование спецификаций

Каждое существенное изменение требований оформляется как **новая версия**
спецификации: обновление существующего `spec.md` с фиксацией даты/статуса
в документе или отдельная папка в `specs/` для крупных пересмотров. Предыдущие
версии сохраняются в истории git.

*Обоснование:* прослеживаемость решений и возможность сравнить «было / стало».

### III. Согласование изменений

Изменения в спецификациях, планах и задачах **MUST** быть согласованы до перехода
к следующему этапу SDD-цикла. Расширение scope дочерней спеки **MUST** быть
отражено в `specs/001-ods-vision/spec.md` до обновления `plan.md` или кода.
Несогласованные правки не являются основанием для обновления `plan.md`,
`tasks.md` или кода.

*Обоснование:* исключает расхождение между видением, требованиями, планом
и реализацией.

### IV. Документация после аппрува

После согласования (аппрува) спецификации **MUST** быть обновлена связанная
документация: `plan.md`, артефакты проектирования (`data-model.md`, `contracts/`,
`quickstart.md`), AsciiDoc-документы проекта — в порядке, определённом затронутой
фичей. Код не меняется до актуализации документации.

*Обоснование:* документация остаётся источником правды для команды и агентов.

### V. Код после документации

Изменения в коде вносятся **только после** обновления согласованной спецификации
и связанной документации (`plan.md`, `tasks.md`). Реализация выполняется по
задачам из `tasks.md` (например, через `/speckit-implement`).

*Обоснование:* соблюдение Spec-Driven Development — сначала артефакты, затем код.

### VI. Иерархия спецификаций ODS

Структура спецификаций ODS **MUST** соблюдать разделение ролей:

- **`001-ods-vision`** — видение, границы MVP/post-MVP, дорожная карта этапов;
  **MUST NOT** содержать детальные FR и user stories для реализации.
- **`002-domain-model`**, **`003-portal-mvp`** и последующие `00N-*` — детальные
  спецификации фич с полным набором разделов шаблона (сценарии, FR, критерии).
- **MVP платформы** = `002` + `003`; видение и границы — в `001`.
- Зависимости между спеками **MUST** быть явными (`Родительская спека`,
  `Зависимость` в заголовке `spec.md`). `003-portal-mvp` зависит от
  `002-domain-model`.

Черновики в `ods-help/requirements/` — источник идей; **MUST NOT** заменять
`specs/**/spec.md`.

*Обоснование:* одна главная спека не раздувается; реализация ведётся по
проверяемым дочерним документам.

## Структура спецификаций ODS

| Этап | Папка | Назначение | Статус |
|------|-------|------------|--------|
| 0 | `001-ods-vision` | Видение, границы, дорожная карта | ✅ согласовано |
| 1 | `002-domain-model` | Модель данных MVP, ES, API | ✅ реализовано |
| 2 | `003-portal-mvp` | Портал: меню, импорт, sync, UI, DELETE | ✅ реализовано |
| 3 | `004-mvp-runtime` | Runtime: CI, deploy, smoke, фикстуры | **отложено** |
| 4 | `005-code-analysis` | Детектор языков, оркестратор, парсеры | черновик требований |
| 5 | `006-project-graph` | Граф в ES, ingest, API | черновик требований |
| 6 | `007-graphify-integration` | Интеграция Graphify в составе ODS | планируется |
| 7 | `008-documentation` | Документация AsciiDoc, PDF | планируется |
| 8 | `009-rag-mcp` | RAG, MCP, внешние агенты | планируется |
| 9 | `010-auth` | Аутентификация и роли | планируется |

Каноническая дорожная карта — `specs/001-ods-vision/spec.md`; при расхождении
приоритет у `001` до следующего `/speckit-constitution`.

**MVP выполнен (2026-07-09):** `002` → `003` → код; пилот на `docker/` (`--profile full`).
**Следующий шаг:** согласовать `ods-help/requirements/data-model-persig-analysis-draft.md`,
затем `/speckit-specify` на `005` и `006`.

Этап `004-mvp-runtime` формализует CI/deploy и **не блокирует** post-MVP анализ.

## Post-MVP: анализ кода (направление для 005/006)

Зафиксировано в `001` и черновике `data-model-persig-analysis-draft.md`:

- **Детектор языков** — первый шаг анализа; отчёт по языкам и файлам проекта.
- **Парсеры — модульные** (отдельный CLI на язык); native JSON на выходе **свой**
  для каждого модуля. **Приоритет `005`:** TypeScript/JavaScript, C#, Python, C++;
  остальные языки — по мере надобности.
- **Канонический граф** — нормализованные метаданные в **Elasticsearch** (`006`),
  не сырой AST и не единый JSON всех парсеров. **Отдельные индексы** (как
  `ods-elements` в `002`), связь через `project_id`.
- **Graphify** (`007`) — отдельный канал, не смешивать с языковыми парсерами.

## Продуктовые ограничения MVP

Следующие решения из согласованных спек **MUST** соблюдаться при планировании
и реализации MVP (этапы 1–2), пока не изменены через `001` и дочерние спеки:

- **Архитектура:** веб-приложение — фронтенд + backend-сервис; деплой через
  **Docker Compose** (каталог `docker/`; профиль `full` — ES + backend + frontend).
- **Стек MVP:** **TypeScript** (фронтенд и backend); альтернативный backend
  (.NET и др.) — только как **parser-модуль** (subprocess) или отдельное решение в `001`.
- **Хранение:** метаданные (проект, дерево, статусы) — **JSON в Elasticsearch**;
  содержимое файлов — **filesystem** рабочей копии.
- **Источник проекта:** Git URL или локальный путь к git-репозиторию.
- **Портал MVP:** единое главное меню; **трёхпанельный** layout; просмотр файлов
  **только read-only**; **удаление проекта** (каскад ES + WC); пункт «Граф» — заглушка;
  **без** бокового TOC.
- **Доступ:** внутренний пилот **без входа** и ролей.
- **Язык UI и артефактов:** русский (`specs/**`, `ods-help/**`, интерфейс портала).

**Вне MVP** (спеки `005+`): анализ кода, парсеры, граф, Graphify, RAG,
редактирование файлов в UI, аутентификация, Git push/merge, PDF/AsciiDoc pipeline.
Этап `004-mvp-runtime` — CI/deploy пилота, не анализ кода.

## Область действия

Конституция распространяется на:

- все артефакты в `specs/**` (спецификация, план, задачи, чеклисты, контракты);
- проектную документацию в `ods-help/**` и будущие AsciiDoc-документы продукта;
- прикладной код ODS-платформы (фронтенд, backend, инфраструктура деплоя).

Инфраструктура Spec Kit (`.specify/templates/`, `.cursor/skills/`, скрипты) **не
подпадает** под правила содержания продуктовых спек и **не переводится** —
это upstream-пакет.

## Порядок SDD-цикла

Обязательная последовательность при внесении изменений в продукт:

1. Актуализация видения и границ в `001-ods-vision/spec.md`
   (`/speckit-constitution` при изменении правил; ручная правка при смене scope).
2. Правка или создание дочерней `spec.md` (`/speckit-specify`, `/speckit-clarify`).
3. Согласование спецификации (и `001`, если меняются границы MVP).
4. Обновление `plan.md` и артефактов проектирования (`/speckit-plan`) —
   **на каждую реализуемую спеку** (`002`, `003`, …).
5. Обновление `tasks.md` (`/speckit-tasks`).
6. Проверка согласованности (`/speckit-analyze`) — в т.ч. `001` ↔ дочерние спеки.
7. Реализация по `tasks.md` (`/speckit-implement`).

Пропуск этапов согласования или документации перед кодом нарушает конституцию.

## Управление

- Конституция имеет приоритет над устными договорённостями и черновиками
  (`ods-help/requirements/` — источник идей, не замена `specs/**/spec.md`).
- Поправки конституции — через `/speckit-constitution` с инкрементом версии
  (semver: **MAJOR** — снятие/переопределение принципа; **MINOR** — новый
  принцип или раздел; **PATCH** — уточнения формулировок).
- После изменения конституции затронутые `specs/**/spec.md`, `plan.md`, `tasks.md`
  **MUST** быть пересмотрены на соответствие (`/speckit-analyze`).
- При ревью PR и планов **MUST** проверяться: соблюдение иерархии спек (пр. VI),
  границы MVP (раздел «Продуктовые ограничения MVP»), порядок SDD-цикла.
- Язык пользовательских артефактов: **русский** (`.specify/memory/constitution.md`,
  `specs/**`, `ods-help/**`).
