## CP1 — API и system на входе в граф

### Цель

После анализа на эталоне (ods-arch): вход в сервис на **system**-слое показывает
`http_endpoint` из **кода** (и уже имеющиеся system-сущности: openapi/bus/БД,
если есть). **Код**-слой по-прежнему символы (`012`).

### Решение

- Модули **`ts-api-routes`** (обязательно), **`dotnet-api-routes`** (P2 внутри CP1
  или follow-up — решить в specify).
- Отдельно от `typescript`/`csharp`; канон `http_endpoint` + `exposes` → `service`;
  опционально ребро к handler.
- `openapi` остаётся; merge/дедуп path+method — clarify (код = runtime-правда).
- Контракт: `parsers/<id>/` + detector + registry + ingest; модуль удаляемый.

### Приёмка CP1 (тест)

1. ods-arch: re-analysis → у `backend` в system-интерьере есть HTTP из Fastify.
2. Code-слой backend — модули, не путать с endpoint-узлами.
3. Выключение парсера не ломает compose/openapi/code.
4. Audit reuse парсеров/ingest — ok.

### Не в CP1

Кнопки «Код»/«Система», срез анализа, крошки в GraphPage, единый sync-оверлей.

## CP2 — UI: кнопки, строки (крошки), окна

**Старт только после зелёной приёмки CP1.**

### Цель

Понятные действия и один поток уведомлений на всех экранах, включая graph-view.

### Решение

| Элемент | Поведение |
|---------|-----------|
| **Код** / **Система** / **Посмотреть в анализе** | Ясные слои; анализ = **только срез** схемы |
| Крошки в анализе | Как в просмотре (`Система › backend`), **Наверх** / **К системе**; общий компонент |
| Прогресс sync/анализа | Один layout-оверлей: сам открылся/закрылся → wizard с стабильными подписями → прогресс анализа; виден и на «Граф просмотр» |

### Приёмка CP2

1. Подписи кнопок согласованы; primary понятен.
2. Из среза backend → анализ только среза + крошки + подъём к Системе.
3. Sync с graph-view → общий оверлей; нет путаницы «Продолжить»/«Запуск».
4. Нет копипасты крошек/прогресса; audit reuse UI — ok.

### Не в CP2

Новые языки API-парсеров, gRPC, docs/RAG/auth.
