## 1. Проблема

После импорта и анализа ODS держит в Elasticsearch канон (проект, дерево,
граф…). Архитектор может *смотреть* систему в Graph view / Graph UI, но нет
пакета **доков** в Markdown, который можно читать в портале (и позже унести
export-pack’ом).

Нужный контур **сейчас**:

1. ИИ точечно читает **только ES** через **REST API** (не WC);
2. пишет **Markdown-доки** (глубина как у наших спек ODS — не «красивый README»);
3. файлы на диске ODS под `DATA_ROOT/docs/{projectId}/`;
4. портал: дерево + viewer.

**Позже:** export-pack (`docs/` + `es-data/`) — только когда доки уже есть.

## 4. Наблюдение: workspace volume vs граф

В `docker/docker-compose.dev.yml`:

- сервис **`elasticsearch`** + volume `es-data` — на Graph view как сервис/инфра;
- volume **`ods-data` → `/data/ods`** (`DATA_ROOT`) — WC импортов + место для доков;
- bind **`LOCAL_REPOS_*` → `/repos:ro`** — `local_path` импорт.

**Почему на графе «есть ES, нет workspace»:** graph показывает сервисы
*анализируемого* репо; `ods-data` — **платформенный** volume ODS. Чинить volumes
на Graph view — backlog, не DoD `015`.

### 4a. Что такое `DATA_ROOT`

**`DATA_ROOT`** — корневая папка на диске **backend** для файлов ODS на ФС
(не Elasticsearch). В compose: `DATA_ROOT=/data/ods` → named volume `ods-data`.
Локально часто `./data`.

| Где | Что |
|-----|-----|
| **ES** | метаданные проекта, дерево путей, граф, analysis run |
| **`DATA_ROOT`** | WC (`working-copies/`), **доки** (`docs/`), **промпты** (`prompts/`) по `projectId` |

Почему «много связано с проектом»: у каждого импорта есть `working_copy_root`
(обычно под `DATA_ROOT`). Sync, чтение файлов, парсеры идут оттуда. Доки
предлагаем класть рядом, но **не внутрь** WC (чтобы git sync не мешал).

Для генерации **доков** ИИ через REST ходит **только в ES-канон** (не в WC).
WC на диске нужна парсерам/sync; доки пишутся в `DATA_ROOT/docs/`, но исходники
репо ИИ для доков не читает.

## 5. Продуктовая модель документации

### 5.1. Что такое «доки»

**Markdown-доки** анализируемой системы (по глубине близки к нашим спекам ODS,
но это **не** файлы в `specs/` этого репозитория):

- vision / границы;
- доменные сущности и связи;
- API / события / UI landscape (structure+function);
- инфра и runtime assumptions;
- критерии приёмки / сценарии.

Формат: **только Markdown**.

### 5.1a. Связь доков с данными ES (зафиксировано 2026-07-25)

Доки не «голый текст»: у файла и у важных сущностей есть привязка к записям
в Elasticsearch, плюс **открываемая HTTP-ссылка** на получение сущности.

#### Уровни

| Уровень | Что | Зачем |
|---------|-----|--------|
| **1. Шапка файла** | `project_id`, `analysis_run_id` | весь файл = один актуальный анализ |
| **2. У сущности** | индекс ES + id записи (+ attrs по желанию) | найти тот же объект в базе |
| **3. HTTP-ссылка** | GET, можно открыть в браузере / вставить в терминал | проверить данные глазами или скриптом |

Отдельный текст `curl` не обязателен: достаточно URL (его же можно вызвать через curl).

#### Два режима адреса (важно)

| Где живут доки | База URL | Что в ссылке |
|----------------|----------|--------------|
| **В ODS** (создание / проверка) | `ODS_BASE_URL` (портал/API, напр. `http://localhost:8080/api/v1`) | endpoint ODS, который отдаёт сущность (контракт уточним в `015`) |
| **После export** (чужая среда) | `BASE_ES_URL` (их Elasticsearch, напр. `http://localhost:9200`) | `BASE_ES_URL` + путь к документу: `/{index}/_doc/{id}` |

В ODS мы контролируем правильность доков по своим API.  
После отдачи pack у получателя **свой** ES и **свой** адрес — поэтому в
export-pack (manifest / README / шапка доков) указывается **`BASE_ES_URL`**,
а в ссылках — уже их хост + тот же index/id.

Стабильный якорь всегда:

```text
index + document id (+ project_id / analysis_run_id)
```

URL — удобная оболочка над якорем; хост подставляется под среду.

#### Пример у сущности (создание в ODS)

```markdown
---
project_id: <uuid>
analysis_run_id: <uuid>
---

### Customers service

Fetch: <ODS_BASE_URL>/projects/<project_id>/…/<node-id>
<!-- es-ref
index: ods-graph-nodes
id: <analysis_run_id>:service:customers
attrs: kind=service, layer=system
-->
```

После export тот же блок логически даёт:

```text
Fetch: <BASE_ES_URL>/ods-graph-nodes/_doc/<analysis_run_id>:service:customers
```

(точный path ODS API — в contracts при specify; path ES `_doc` — стандартный.)

ИИ **MUST** писать уровни 1–2 всегда; уровень 3 — как видимая HTTP-ссылка
рядом с важной сущностью (не только скрытая пометка).

### 5.2. Кто пишет / кто читает

| Роль | Статус |
|------|--------|
| Автор текста | **Внешний** ИИ-агент (Cursor / Claude Code / …) по REST; ODS в MVP LLM не запускает |
| Доступ к данным (доки) | **REST API → только ES** (**MUST NOT** читать WC) |
| Хранилище доков | `DATA_ROOT/docs/{projectId}/` |
| Export-pack | **Позже**, когда доки есть — не первый шаг |
| Сборка кода из доков | Вне ODS |

### 5.3. Где лежат файлы

Не смешивать с git WC.

```text
DATA_ROOT/
  working-copies/{projectId}/     # WC репозитория
  docs/{projectId}/               # Markdown-доки + AGENT.md (промпт проекта)
```

Шаблоны продукта в git: `prompts/docs-agent-prompt.md` (и stub `code-agent-prompt.md`).
Отдельной папки `DATA_ROOT/prompts/{projectId}/` для S2 **нет** — отрендеренный
промпт живёт **внутри** `docs/{projectId}/` (§7.5, §10.5).
Дерево папок **доков** — §10.1.

| Этап | Когда | Смысл |
|------|-------|--------|

| **2. Export-pack** | **Позже**, только если доки есть | Бэкенд собирает и отдаёт одним `.zip`: `docs/` (включая `AGENT.md`) + `es-data/` |

Без доков export не предлагаем.

#### Export-pack (зафиксировано; реализация позже)

- Кнопка **Export** — в правой панели «Документация», ниже
  **«Скачать промпт»**.
- Пока docs AiJob не `succeeded`, кнопка disabled.
- По клику **бэкенд** собирает и отдаёт один файл
  `export-{projectId}-{timestamp}.zip`; фронт только начинает download.
- Назначение pack: передать доки + данные другому человеку / на другой
  компьютер для оценки и как вход для отдельной попытки собрать новую систему.
- **Граница:** ODS гарантирует pack, но не собирает новую систему и не обещает
  точное восстановление исходников. Эта работа выполняется снаружи ODS.

```text
export-{projectId}-{timestamp}.zip
└── export-{projectId}-{timestamp}/
  docs/                 # Markdown-доки + AGENT.md (промпт, по которому собирали)
  es-data/              # вырезка актуального ES-среза проекта
    manifest.json
    ods-*.ndjson
  README.md
```

`AGENT.md` **MUST** входить в export вместе с доками — история «по какому
промпту собрали». `manifest.json` / `README.md` документируют
`BASE_ES_URL`, который получатель указывает для своего Elasticsearch.

### 7.4. Как устроен ES и что кладём в `es-data`

#### Модель данных проекта (решение 2026-07-24)

В живом ODS **одна** Elasticsearch на все проекты. Данные в **общих индексах**
с полем `project_id` (какой импортированный репозиторий).

| Индекс | Ключ | Что хранит |
|--------|------|------------|
| `ods-projects` | `_id` = project id | карточка проекта |
| `ods-elements` | `project_id` | дерево файлов WC (sync) |
| `ods-sync-snapshots` | `project_id` | снимок sync |
| `ods-language-reports` | `project_id` | отчёт языков |
| `ods-analysis-runs` | `project_id` | **один** актуальный run (см. ниже) |
| `ods-parser-envelopes` | `project_id` + `analysis_run_id` | вывод парсеров |
| `ods-graph-nodes` | `project_id` + `analysis_run_id` | канон-узлы |
| `ods-graph-edges` | `project_id` + `analysis_run_id` | канон-рёбра |

**Решение владельца — один полный актуальный граф, без инкремента и без
истории runs** (сделать **при старте `015`**, код/`006` в этом чате не трогаем):

- На проект снаружи всегда **один полный актуальный граф**, связанный с
  импортируемым репозиторием (`project_id` + актуальный `analysis_run_id`).
- Поля `project_id` и `analysis_run_id` в документах **оставляем** (модель/
  ingest/API).
- **Анализ всегда полный** (весь WC / все релевантные парсеры). Инкремент
  (`change_set.incremental`, bootstrap/`copyFromRun`, path-scoped
  delete-before-upsert) **убираем**.
- Чекбокс / флаг **`force_full` / «полный анализ» убираем** — он больше не нужен.
- Модалка «что изменилось после sync» **MAY** остаться информационной; она
  **не** управляет объёмом анализа.
- **Замена графа (важно):** не «сначала стереть, потом собрать».
  ```text
  сейчас:  [граф A]  ← UI
  запуск:  собираем новый полный [граф B] рядом (A жив)
  успех:   UI → B, A удаляем
  провал:  UI → A, недоделанный B выкидываем
  ```
  Снаружи всегда один граф; старый — только страховка до успеха нового.
- Почему не инкремент: один алгоритм; кросс-файловые рёбра не «протухают»
  от path-патча; проще модель для доков/export. Цена — дольше на больших репо
  (прогресс уже есть из `010`).

> Prerequisite при старте `015` (или мини-fix перед ним): правка поведения
> `005`/`006` под правила выше. Пока — только в этом черновике.

```text
ES (цель):
  project A → ровно один актуальный полный analysis_run + граф
  project B → …
```

#### Что экспортируем в `es-data/`

**Только данные этого проекта в актуальном состоянии** = всё по `project_id`
+ граф/envelopes этого (единственного) `analysis_run_id`:

| Слой | В pack |
|------|--------|
| `ods-projects` | да (1 документ) |
| `ods-elements` | да (все по project_id) |
| sync / language report | да (актуальные) |
| `ods-analysis-runs` | да (**один** актуальный) |
| nodes / edges / envelopes | да (**этот** analysis_run_id) |

Чужие проекты — нет. Старые runs — **уже нет в ES**, значит и в pack нет.

`manifest.json`: `project_id`, единственный `analysis_run_id`, список индексов.

#### Зачем вырезка, а не россыпь JSON

Выгружать JSON «как попало» плохо. Нужна **мини-база того же вида**, что живой
ODS (те же `ods-*`, те же поля), только на один проект — чтобы снаружи в
Cursor + свой ES было единообразно, а доки ссылались на ту же вырезку
(`es-ref`, §5.1a).

**Граница (жёсткая):** ODS отдаёт pack = `docs/` + `es-data/`. Дальше —
**не обязанность ODS** (Cursor, свой ES, сборка системы). Не DoD
воспроизведения в портале и не импорт в другой ODS.

```text
живой ODS:  ES (актуальный граф на project_id) + UI
export →    es-data/ (тот же project_id + analysis_run_id) + docs/
потом:      свой ES ← bulk  +  docs/ в Cursor
```
Технически export: scroll по `project_id` (+ единственный `analysis_run_id`
для graph/envelopes) → NDJSON/`_bulk` (+ mappings в manifest) → снаружи
create index + bulk. Потребитель получает ту же «базу ES», только на один проект.

| Подход | Суть | Плюсы | Минусы |
|--------|------|-------|--------|
| **NDJSON + `_bulk`** (предпочтение v1) | Вырезка актуального проекта; restore = mappings + bulk | Тот же формат, что живой ODS | Export-endpoint; restore снаружи |
| **elasticdump / аналог** | То же готовым tool | Меньше кода | Зависимость tool |
| **ES Snapshot** | Официальный snapshot | «Как бэкап кластера» | Плохо режет один проект |

**Сценарий «потом» (вне ODS):**

```text
1. ODS: доки готовы → Export-pack (docs/ + es-data/) + README
2. Cursor: открыть docs/
3. По желанию: свой ES ← bulk es-data/ → граф + доки (es-ref)
4. Сборка системы — целиком вне ODS
```

**Оговорки:** WC в pack по умолчанию нет; DoD ODS = **pack + README**; Import в
другой ODS — не в v1.


### 7.5. Промпт + REST: доставка задания агенту (зафиксировано 2026-07-25)

**База:** ODS даёт REST. Агент читает ES и пишет доки через API. MCP — потом.

#### Где лежат шаблоны и куда пишется промпт проекта

| Что | Где |
|-----|-----|
| Шаблон доков (S2) | репо: `prompts/docs-agent-prompt.md` (поставка backend/образа) |
| Шаблон кода/графа (S1) | репо: `prompts/code-agent-prompt.md` (stub; путь проекта TBD после `015`) |
| Промпт **этого** проекта | **`DATA_ROOT/docs/{projectId}/AGENT.md`** (не WC, не отдельный `prompts/`) |

```text
DATA_ROOT/
  working-copies/{projectId}/
  docs/{projectId}/
    AGENT.md              # промпт проекта; provenance; не spec системы
    spec-….md             # после генерации
    …
```

Не bind-mount git ODS в volume: шаблон **копируется/рендерится** из поставки
backend в `docs/{projectId}/AGENT.md`.

#### Жизненный цикл `AGENT.md`

1. **При импорте проекта** — создать `docs/{projectId}/` и положить туда
   `AGENT.md` (seed из шаблона; как минимум `PROJECT_ID`; остальные
   плейсхолдеры могут ждать анализа / «Скачать промпт»).
2. **«Документация»** сразу после импорта — дерево не пустое: виден `AGENT.md`
   (viewer; редактор in-ODS — optional later).
3. **«Скачать промпт»** — перерендерить `AGENT.md` на месте (`ODS_BASE_URL`,
   `ANALYSIS_RUN_ID`, `DOCS_LANGUAGE`, write-mode, …) + download файла.
   Повторно качать **не обязательно**, если файл уже актуален: агент может
   читать `AGENT.md` из ODS по REST.
4. **Внешний агент** (Cursor / Claude / …) по инструкции из `AGENT.md` ходит
   в REST ODS → пишет `spec-*.md` **рядом**, **MUST NOT** затирать `AGENT.md`.
   ODS в MVP **не** запускает ИИ сам.
5. **Export-pack** — уносит весь `docs/` **включая** актуальный `AGENT.md`,
   чтобы позже видеть, по какому промпту собрали доки.
6. Режим `versioned` — копия `AGENT.md` также под
   `_generations/{DOCS_GENERATION_ID}/AGENT.md`.

#### `ODS_BASE_URL` (инфра)

- В git-шаблоне — только placeholder.
- В инстансе — env вроде `PUBLIC_API_BASE_URL` **или** origin портала при клике.
- Локальный `--profile full` (портал `:8080`): **`http://localhost:8080/api/v1`**
  (nginx проксирует `/api/` → backend). Проверено: `GET .../health` → ok.
- В другой инфре меняется env/host, не правка файла в git.

#### Кнопка «Скачать промпт» + свойства доков (правая панель)

Макет правой панели (сверху вниз, как свойства на других экранах):

1. **Свойства / статистика доков** (из AiJob + дерево файлов), например:
   - статус последнего job: `none` / `running` / `succeeded` / `failed`;
   - `analysis_run_id`, язык (`docs_language`);
   - число `spec-*.md` / файлов; время finished;
   - краткий summary агента (gaps, ошибки REST) если есть.
2. Контроль языка `en`/`ru` (дефолт = locale портала).
3. Одна постоянная кнопка **«Скачать промпт»** (не переименовывать в «пересоздать»).

Поведение кнопки:

1. При необходимости создаёт/обновляет AiJob `docs_from_es` (`running`) и
   вписывает `DOCS_JOB_ID` в `AGENT.md`.
2. Берёт шаблон `prompts/docs-agent-prompt.md` (или текущий `AGENT.md`).
3. Подставляет `ODS_BASE_URL`, `PROJECT_ID`, `ANALYSIS_RUN_ID`,
   **`DOCS_LANGUAGE`**, write-mode, `DOCS_JOB_ID`, …
4. Пишет / обновляет `DATA_ROOT/docs/{projectId}/AGENT.md` + **download**.
5. Активна после успешного анализа (нужен текущий `analysis_run_id`).

#### Завершение работы агента → UI

Агент в конце **MUST** обновить AiJob по REST (`succeeded` / `failed` +
summary). Бэкенд хранит статус; фронт (poll/WS) обновляет **свойства** в
правой панели и дерево. При `succeeded`:

- enable Export (когда export появится);
- тост «Доки сформированы» + опционально действие «Открыть Export»;
- **не** авто-открывать модалку Export без клика пользователя.

Агент **не** дергает фронт напрямую — только backend API.

Минимальный REST для S2: graph/reports read; docs list/read/write;
AiJob create/progress/complete.

**MCP потом** — tools над теми же handlers.

## 8. Два ИИ-сценария: что общего и как спланировать пайплайн

В продукте будут **два разных применения ИИ**. Их нельзя смешивать по входу/выходу,
но **каркас job’ов** лучше заложить общим сразу.

### 8.1. Сценарии рядом

| | **S1 — ИИ → граф** (позже, не `015`) | **S2 — ИИ → доки** (`015` сейчас) |
|--|--------------------------------------|-------------------------------------|
| Когда | Импорт / анализ, mode=ИИ вместо парсеров | После того как граф уже в ES |
| Читает | **WC** (исходники) | **Только ES** |
| Пишет | Канон в ES (nodes/edges/…), `provenance=ai` | Markdown в `DATA_ROOT/docs/` |
| Замена чему | Модульные парсеры + ingest | Ручные/отсутствующие доки |
| UI | Модалки анализа / progress анализа | Экран «Документация» / docs job |
| Риск провала | Дырявый или кривой граф | Плохой текст; граф не тронут |

```text
S1 (future):  WC ──ИИ──► ES canon
S2 (015):     ES canon ──ИИ──► docs/
```

Цепочка во времени: обычно **сначала S1 или парсеры → ES**, потом **S2 → доки**.
S2 **не** требует S1: при парсерах S2 всё равно работает (только ES).

### 8.2. Что одинаковое (имеет смысл унифицировать)

| Общий кусок | Зачем |
|-------------|--------|
| **AiJob** (`kind`, `project_id`, status, progress, errors, started/finished) | Один статусный контур в API/UI |
| Доставка задания агенту | Для S2 MVP: render `AGENT.md` + download; внешний агент; in-process LLM — later |
| Provenance: модель, время, input fingerprint | Повторяемость, отладка |
| REST-поверхность «для агента» | Один стиль tools: read X / write Y |
| Playbook / этапы (не один гигантский промпт) | И граф, и доки лучше кусками |
| Политика «не ломать канон» | S1 пишет в **тот же** shape, что парсеры; S2 только читает |

Черновой общий контракт:

```text
AiJob {
  id, project_id
  kind: "graph_from_wc" | "docs_from_es"
  status: queued|running|success|failed|cancelled
  progress: { stage, percent?, message }
  provenance: { model_or_agent, started_at, finished_at }
  // kind-specific:
  //  graph_from_wc → analysis_run_id (новый полный граф, replace-after-success)
  //  docs_from_es  → analysis_run_id (актуальный) + docs_path
}
```

### 8.3. Что разное (отдельные адаптеры, не один «универсальный ИИ»)

| | S1 graph_from_wc | S2 docs_from_es |
|--|------------------|-----------------|
| Reader | файлы WC (path allowlist, лимиты размера) | REST graph/reports по project |
| Writer | ingest-совместимый канон → ES | Markdown + `es-ref` → `DATA_ROOT/docs/` |
| Валидация | schema канона / counts / smoke graph | наличие доков, наличие es-ref |
| Права | читать WC; писать ES | читать ES; писать docs; **не** WC |

**Не делать:** один промпт «прочитай репо и сразу напиши доки» — ломает границу
S2 и смешивает ответственность парсеров/графа с документацией.

### 8.4. План (подтверждено владельцем 2026-07-25)

1. **В `015`:** S2 (`docs_from_es`) + заложить общий **AiJob / runner / status API**;
   первый клиент — `kind=docs_from_es`.
2. **Следующая фича (S1):** `kind=graph_from_wc` + WC reader + canon writer;
   переключатель Парсеры/ИИ на импорте; **без** ломки контракта AiJob.
3. **S2 MVP:** внешний агент + «Скачать промпт»; in-process LLM в ODS —
   later (отдельное решение). Транспорт данных — **REST**; MCP later.
4. MCP later — обёртка над теми же REST tools.

**Итог (зафиксировано):** пайплайны близкие по каркасу, разные по адаптерам;
не одна фича, но общая шина ИИ-задач. Не смешивать входы/выходы S1 и S2.

### 10.1. Дерево доков повторяет систему в графе (зафиксировано)

**Правило:** папки и вложенность = иерархия system-слоя графа. Имена из графа
(безопасный slug). Главный файл компонента — **`spec-{имя}.md`**, не `README.md`.

```text
docs/{projectId}/
  AGENT.md                          # промпт проекта (с импорта); не spec
  spec-{имя-проекта}.md             # обзор всей системы (после генерации)
  {компонент}/
    spec-{компонент}.md             # док компонента
    contracts/                      # только если данные есть в ES
      openapi.md
      asyncapi.md
      rpc-grpc.md
    messaging/
      kafka.md
      rabbitmq.md
    data/
      databases.md
    infrastructure/
      runtime.md
    {дочерний}/
      spec-{дочерний}.md
      …
```

`AGENT.md` — зарезервированное имя в корне docs; агент **не** создаёт и **не**
перезаписывает его (это делает ODS). Не путать с WC анализируемого репо.

#### Имя корневого `spec-{имя-проекта}.md`

Брать в порядке:

1. `project.name` из ODS (задали или получили при импорте);
2. иначе имя репо из git URL / последней части `local_path`;
3. для ФС — безопасный slug (`My Repo` → `my-repo`).

В шапке файла: исходное имя, `project_id`, `analysis_run_id`, es-ref на
корневой/системный узел, если есть.

Отдельный корневой `README.md` **не** нужен: корневой `spec-{имя-проекта}.md`
и есть карта системы + ссылки на дочерние `spec-*.md`.

#### Обязательные разделы каждого `spec-*.md`

1. **Назначение** — зачем компонент существует и его границы.
2. **Состав** — дочерние компоненты, модули и ключевые сущности.
3. **Принцип работы** — основные потоки, взаимодействия и жизненный цикл.

Дополнительные разделы / файлы — **только при наличии данных в ES**:

- контракты: OpenAPI, AsyncAPI, RPC/gRPC;
- связи: HTTP, Kafka, RabbitMQ и другие;
- базы данных и хранилища;
- runtime / инфраструктура;
- UI-часть компонента;
- зависимости от других компонентов.

#### Правила, чтобы дерево не разрослось

- Отдельная папка — только для **архитектурно значимого контейнера**
  (system/service/module/UI app и т.п. с дочерними узлами).
- Не создавать папку на каждый class/method/endpoint/control — листья в
  `spec-*.md` родителя или тематическом файле.
- Имя папки / файла = slug; исходные `name`, canonical id и es-ref — в шапке.
- При неизвестной иерархии — `GAP`, не выдумывать родителей.

Шаблон этой структуры **MUST** быть и в vision draft (§10.1), и в
`prompts/docs-agent-prompt.md` (синхронно).

### 10.2. Найденный пробел покрытия RPC/gRPC/AsyncAPI

- **gRPC/RPC parser отсутствует**; `009` помечает gRPC как Phase 2, `019`
  откладывает gRPC/RSocket/SOAP в Post-MVP.
- `rpc_handles` в каноне system edge относится к RPC-роли bus handler и
  **не означает**, что реализован gRPC/protobuf parser.
- **AsyncAPI parser тоже не найден**.
- OpenAPI, Kafka и RabbitMQ покрыты существующими parser-модулями.

Следствие для доков: агент создаёт `rpc-grpc.md` / `asyncapi.md` только если
соответствующие данные реально появились в ES; сейчас ожидаем `GAP / UNKNOWN`,
не выдумываем контракты. Это отдельный coverage backlog, не блокер структуры
доков.

### 10.3. Версионирование доков (зафиксировано)

**MVP по умолчанию: перезапись** тех же путей под `docs/{projectId}/`.

| Режим | Когда | Куда пишет агент |
|-------|-------|------------------|
| `overwrite` (default) | обычный прогон / MVP | `docs/{projectId}/…` — перезапись файлов по тем же relative path |
| `versioned` (debug) | только если явно в промпте | `docs/{projectId}/_generations/{DOCS_GENERATION_ID}/…` — текущее дерево **не** трогать |

Плейсхолдеры в `prompts/docs-agent-prompt.md` / `AGENT.md`:

- `DOCS_WRITE_MODE=overwrite|versioned` — unset → `overwrite`;
- `DOCS_GENERATION_ID` — обязателен при `versioned`; иначе агент **MUST**
  остановиться с ошибкой (не выдумывать id, не тихо перезаписывать).

В шапке файлов при `versioned` — поле `generation_id`. Очистка orphan-файлов
при overwrite и продуктовое хранение истории — позже.

### 10.4. Язык генерируемых Markdown (зафиксировано)

**Источник:** контроль языка на UI рядом с «Скачать промпт» — **`en` | `ru`**
(как i18n портала).

**Дефолт:** текущий **locale портала**, пока пользователь не сменил значение.

При рендере `AGENT.md` ODS подставляет в промпт вместе с путями/URL:

- `ODS_BASE_URL`, `PROJECT_ID`, `ANALYSIS_RUN_ID`, …
- **`DOCS_LANGUAGE=en|ru`** — выбранное (или дефолтное) значение.

Правила для агента (см. `prompts/docs-agent-prompt.md`):

- весь человекочитаемый Markdown — на `DOCS_LANGUAGE`;
- канонические имена/id/пути/кодовые токены из ES **не** переводить;
- в YAML front matter каждого файла — `docs_language`;
- если язык не `en`/`ru` или не передан — стоп с ошибкой, не угадывать.

### 10.5. Промпт в `docs/` и provenance (зафиксировано)

- При **импорте** создать `docs/{projectId}/` и seed `AGENT.md` из продуктового
  шаблона.
- «Документация» показывает дерево сразу (пока только промпт — нормально).
- При генерации / export промпт **остаётся рядом с доками** и уходит в pack —
  история «по какому промпту собрали».
- Viewer `AGENT.md` в портале — да (MVP); edit/save in-ODS — later optional.
- Отдельный `DATA_ROOT/prompts/{projectId}/` для S2 не используем.

### 10.6. UX правой панели «Документация» (зафиксировано)

| Элемент | Решение |
|---------|---------|
| Где | Экран **«Документация»**, **правая панель свойств** (как на других страницах) |
| Сверху | **Свойства доков**: статус AiJob, язык, `analysis_run_id`, счётчики файлов, summary/gaps, finished at |
| Ниже | Контроль языка `en`/`ru` (дефолт = locale портала) |
| Кнопка | Одна постоянная: **«Скачать промпт»** (не менять на «пересоздать») |
| Что делает кнопка | Refresh `AGENT.md` + download; при необходимости AiJob → `running` |
| Когда активна | После успешного full-анализа |
| Кто пишет доки | **Внешний** агент по REST; ODS в MVP **не** стартует ИИ |
| Финиш агента | REST → AiJob `succeeded`/`failed` + summary; UI обновляет свойства; enable Export; тост (без авто-модалки) |
| Export | Ниже «Скачать промпт»; backend отдаёт один `.zip`; disabled до `succeeded` |
| Повтор | Качать снова не обязательно, если `AGENT.md` актуален |

Позже (не MVP): опциональная кнопка «запустить агента в ODS» — отдельное решение.
