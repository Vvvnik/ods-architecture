# Видение проекта

> **Связанные материалы:** архитектура MVP анализа кода — [`text-2.md`](text-2.md),
> модель графа — [`text-3.md`](text-3.md), схема — [`schema.puml`](schema.puml).
> Спецификация этапа 0 — `specs/001-ods-vision/spec.md` (актуализируется через Spec Kit).

1. Мы не будем подстраиваться под Backstage и его структуру!
2. Напишем спецификации для создания своего приложения.
3. Оно при открытии проекта исходного кода показывает его файловую структуру. Можно открывать и просматривать обычным редактором. Пока без плагинов для API, диаграмм и др., просто текстовые файлы кода.
4. Импортируем проект в наш формат с помощью **языковых парсеров** (Roslyn, TypeScript AST и др.): ждём завершения анализа и получаем структуру и графы для просмотра.
5. Можно редактировать, удалять лишнее, заносить в список, например: нужен, не нужен, найден, не используется и т.п. По умолчанию всё находится в статусе «найдено скриптом».
6. Структурные данные платформы (проекты, статусы, метаданные) — **рассмотреть целесообразность** PostgreSQL или другой реляционной БД; окончательный выбор на этапе 1 (domain model).
7. RAG и векторный поиск — **рассмотреть целесообразность** ChromaDB или аналога; окончательный выбор на этапе 10 (`010-rag-mcp`); для графа кода на этапах 5–6 ориентир — Elasticsearch (см. `text-2.md`).
8. Можем сделать строки поиска для ИИ и всего, чего захотим.
9. Подключаем к нему агентов, Telegram и других агентов, чтобы можно было спросить, например, как добавить новую функцию или как исправить ошибку. Система показывает по нашим данным, какие файлы проекта и в каких папках надо править.
10. Тут же можно писать задачи на доработку, но нужна интеграция с Git – это пока держим в уме.
11. Файлы ТЗ и спецификаций можно составлять прямо там, а потом открывать в Cursor и запускать правки. Но это можно продумать позже.
12. Документацию делаем, как привыкли, в AsciiDoc: основной каркас, а мелкие документы, которые генерирует ИИ, вставляем через include.
13. Создаём свои CSS для портала, чтобы было прилично: навигационное меню, оглавление и т.д.
14. Заводим шаблоны документов для PDF. Они у нас уже есть, я делал их в ODS и знаю, как перенести в наш фронтенд.
15. Делаем колонку с визуальным редактором стилей и шрифтов. Она редактирует наши файлы настройки печати PDF. Там же запускаем генерацию, просматриваем результат и при необходимости редактируем.
16. Всё в одном интерфейсе, без терминала!
17. Тогда нам не надо будет делать два-три портала – всё будет в одном месте, в нашей ODS-инфраструктуре.
18. Думаю, с ИИ это решаемо. Сложно, но решаемо!
19. Страницы Wiki как legacy из Миртеха или ещё откуда-то просто импортируем в HTML или Markdown. Потом решим, что удобнее.
20. Создавать и редактировать файлы можно прямо в нашем приложении.
21. Проверяем, пушим, мержим в Cursor – пока так. Не знаю, как это лучше придумать, может быть с ИИ это уже не проблема.

## Правила внесения изменений

1. Изменяется только нужная спецификация.
2. Создаётся новая версия спецификации.
3. Изменения согласовываются.
4. После аппрува обновляется документация.
5. После этого вносятся изменения в код.
