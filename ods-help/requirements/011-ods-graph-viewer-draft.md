## Цель

Два разных способа работать с графом:

1. **Граф анализ** — текущий экран (дерево, поиск, таблица рёбер): разобрать
   символы и связи списками.
2. **Граф просмотр** — новая интерактивная схема (React Flow): увидеть контур
   системы и проваливаться внутрь **по уровням**, не перегружая картинку.

Оба читают один и тот же канон в ES. Редактировать граф нельзя.

## Проблема сейчас

| Есть | Не хватает |
|------|------------|
| Один пункт меню «Граф» = списки | Отдельный экран «смотреть схему» |
| Дерево / поиск / 1-hop рёбра | Карта «кто с кем»: сервисы + БД + шины + … |
| Всё в одной куче kinds | Понятный вход: система → участник → глубже |

## Видение

### Одна фраза

**Сверху — карта участников системы (сервисы, БД, шины…); клик — внутри
выбранного + снаружи только то, что связано с ним.** Не рисуем весь граф сразу
и не тащим на холст чужие внутренности.

### Уже решено (из обсуждения)

- Подписи меню: **«Граф анализ»** / **«Граф просмотр»**.
- Уровень 0: прикладные сервисы **и** инфро-peer'ы (каждая БД / Rabbit / Kafka — свой узел).
- Правило холста: фокус + только внешние связи; внутренности соседей не раскрываем.
- БД в MVP `011`: плоский узел из канона + кто подключён; иерархию физика→логика→схема
  не рисуем (нет в парсинге) — держим как целевой UX (§3a–3c).
- Детали 1–6 — в разделе «Предложенные ответы» (ждут финальной ОКции).

### Два пункта в левом меню

| Пункт меню | Маршрут (черновик) | Что это |
|------------|-------------------|---------|
| **Граф анализ** | `/projects/:id/graph` (текущий) | Бывший «Граф»: дерево узлов, поиск, EdgeTable. Переименовать пункт меню. |
| **Граф просмотр** | `/projects/:id/graph-view` (новый) | Canvas React Flow, drill-down по фокусу. |

```text
Меню ODS
  ├── … workspace …
  ├── Граф анализ      → списки (006/007)
  └── Граф просмотр    → схема (011)
```

Связка между экранами (желательно): из анализа «Открыть на схеме» / из просмотра
«Показать в анализе» — тот же `nodeId`, без обязательной синхронизации в реальном
времени на оба экрана сразу.

### Главное правило холста: фокус + внешние связи

На любом уровне:

1. **Внутри фокуса** — содержимое выбранной сущности (сервис, модуль, …).
2. **Снаружи** — только узлы, с которыми у фокуса (или его внутренностей) есть
   рёбра; показываем их **упрощённо** (ярлык + связь), без раскрытия их внутренностей.
3. Всё остальное системы **не рисуем**.

Пример: открыли сервис `Api`. На схеме:

- внутри: то, что относится к `Api` на этом уровне;
- снаружи: `Orders`, Postgres, топик Kafka — если с `Api` есть связь;
- сервис `Billing`, с которым связей нет — **нет на холсте**.

### Уровни drill-down (сущности)

Наверху — не только «приложения», а **все крупные участники системы** на одной
карте. В быту можно называть их «сервисы и инфро», в каноне `009` у них разные
`kind`, но уровень 0 один.

**Уровень 0 — кто на карте (все — отдельные узлы):**

| Участник | kind (пример) | Правило |
|----------|---------------|---------|
| Прикладной сервис | `service` | Каждый сервис — свой узел |
| База данных | `database` | Несколько CS/имён → **несколько** узлов. В MVP — плоский peer; целевая иерархия — §3a |
| Шина / брокер | `broker` | Rabbit и Kafka — **разные** узлы (не одна «шина») |
| Топик / очередь | `message_topic` | В норме **внутри** брокера (не peer на уровне 0); если брокер не извлечён — peer, чтобы не потерять узел (§3d) |
| Внешнее API | `external_api` | Отдельный узел на каждого внешнего контрагента |
| Прочее infra | `storage`, … | Тоже peer на уровне 0, не «прячем внутрь первого сервиса» |

Важно: инфраструктура **не внутри** одного сервиса на карте системы — она
рядом, потому что ей могут пользоваться многие. Связи (`connects_to`,
`publishes` / `consumes`, `depends_on`, `http_calls`…) показывают, кто к чему
подключён.

Глубже (после выбора участника) — **уровни детализации**, без classes/methods
на первом экране.

```text
Уровень 0 — Система (участники)
  узлы: service + database + broker + external_api (+ topic только если нет брокера)
  рёбра: depends_on, http_calls, publishes/consumes, connects_to, …

        ↓ вход в участника
          service  → внутри system-части (§1)
          broker   → внутри topics (§3d)
          database → inspector + связанные сервисы, без фейковых схем (§3c)

Уровень 1 — Внутри выбранного
  внутри: крупные части фокуса (если для kind есть данные)
  снаружи: только связанные участники как порты

        ↓ клик по внутренней сущности / внешнему соседу (смена фокуса, §2)

Уровень 2+ — Глубже внутри фокуса
  тот же принцип: содержимое выбранного + внешние соседи упрощённо
```

**Что внутри сервиса на уровне 1 (MVP):**

| Показывать | Почему |
|------------|--------|
| `http_endpoint`, `dotnet_project` (если есть) | Крупные «входы» и куски сервиса из system-слоя |
| Связи наружу (http_calls, publishes, connects_to…) | Порты к другим сервисам / БД / шине |

**Что обычно не показывать на уровне 1:** тысячи `class` / `method` — это уровень 2+
(code), иначе холст снова превратится в свалку.

**Уровень 2+ (черновик порядка):**

1. модуль / проект / пакет (если есть в каноне / по `parent_id`);
2. тип (`class` / interface…);
3. при необходимости метод — только по явному входу, не стартовый экран.

Хлебные крошки на «Граф просмотр»: `Система › Api › …` + кнопка «Наверх».

### Открытие «Граф просмотр»

При первом заходе — **уровень 0 (Система)**: самый крупный осмысленный граф —
сервисы и общая инфраструктура, **без** детализации кода.

Дальше только drill-down по клику (или double-click / кнопка «Войти»).

### Почему так, а не иначе

| На уровне 0 | Оценка |
|-------------|--------|
| **service + infra peer'ы** (БД, Rabbit, Kafka, внешние API…) | ✅ Карта системы «как у архитектора»; разные инстансы = разные узлы |
| Одна общая нода «Базы» / «Шины» | ❌ Скрывает, кто к какой БД/шине ходит |
| Сразу class/method | ❌ Шум; это анализ и глубокий drill |
| Только файлы / дерево WC | ❌ Это workspace, не граф зависимостей |

### Принцип масштаба (после `010`)

| Правило | Ориентир |
|---------|----------|
| Hard cap узлов на холсте | ~150–250 |
| Hard cap рёбер | ~400–600 |
| Уровень 0 | только system overview (service + shared infra) |
| Drill-down | не подгружаем внутренности невыбранных соседей |
| При превышении cap | сообщение на русском; предложить сузить / другой фокус |

Позиции узлов после auto-layout — MAY только в сессии; **не** в Elasticsearch.

### UX холста (MVP)

1. Pan / zoom / fit-view; крошки уровней; «Наверх» / «К системе».
2. Узлы: имя + вид по `kind` (цвет/форма); внешние соседи визуально отличимы
   (например «внешний» стиль / меньше деталей).
3. Рёбра: тип (подписи i18n); при плотности — подпись по hover/select.
4. Клик по узлу вне «войти»: inspector / список связей (компактно).
5. Войти: **service** (system-содержимое), **broker** (топики); **database** —
   фокус с inspector + сервисы-соседи, без выдуманных схем.
6. Пустые состояния — те же смыслы, что у графа без анализа (`006`).

### Данные и API

Основной контракт просмотра — endpoint в духе (§4):

```text
GET .../graph/view
    ?focus=<nodeId|null>     # null = уровень «Система»
    &depth=system|inside     # или уровень из крошек
    &limit_nodes=&limit_edges=
```

Ответ: узлы внутри фокуса + stub-узлы внешних соседей + рёбра между ними.
Точный контракт — в plan `011`.

`focus=null` — overview system-слоя (сервисы + infra-peer'ы; топики — по §3d).

В MVP `011` ingest/парсеры **не расширяем** ради canvas (иерархия БД — follow-up
данных, §3c). Задел `parent_id` / `service_id` — только если drill сервиса
ломается на пилоте (§6).

### Вне scope `011` — чего не делаем

Схема только **показывает** то, что уже построил анализ.

| Не делаем | По-простому |
|-----------|-------------|
| Редактирование графа | Нельзя руками добавить/удалить узел или связь. |
| Аннотации и `not_needed` | Не помечаем и не прячем узлы «не нужен» — later (`001`). |
| Сохранение расстановки | Координаты узлов не пишем в Elasticsearch. |
| Весь индекс на холст | Не рисуем все узлы проекта разом. |
| Фейковая иерархия БД | Не рисуем физика/схема, если узлов нет в каноне. |
| Поиск на экране просмотра | Ищем в «Граф анализ» (§5). |
| Прочее later | Экспорт картинки/GraphML, RAG, auth; парсер иерархии БД; не заменяем дерево файлов. |

## User stories (черновик)

### US1 — Два пункта меню

Given портал, When смотрю левое меню, Then вижу **«Граф анализ»** (бывший Граф)
и **«Граф просмотр»** (новый экран схемы).

### US2 — Старт просмотра = карта системы

Given есть system-узлы после `009`, When открываю «Граф просмотр»,
Then вижу граф уровня «Система» (сервисы + связанная infra), без classes/methods.

### US3 — Вход в участника (сервис или infra)

Given уровень «Система», When вхожу в участника U,
Then на холсте только связанные с U внешние узлы; чужие участники без связей
с U отсутствуют.

| Kind | Внутри фокуса (MVP) |
|------|---------------------|
| `service` | system-дети (`http_endpoint`, …) — обязательно |
| `broker` | `message_topic` (если есть) |
| `database` | пусто по иерархии; inspector (engine, имя) + сервисы с `connects_to` снаружи |

### US4 — Drill-down глубже

Given фокус внутри участника, When вхожу в дочернюю сущность,
Then снова правило «внутри фокуса + внешние связи упрощённо»; крошки позволяют
подняться вверх.

### US5 — Связка с «Граф анализ»

Given узел на схеме или в анализе, When «Открыть в …», Then другой экран
открывается с тем же проектом и по возможности тем же `nodeId`.

### US6 — Large repo

Given большой `node_count` после `010`, When открываю просмотр,
Then не качаем весь индекс; cap и сообщения на русском; UI не зависает.

## Критерии успеха (черновик SC)

- **SC-01:** На `system-landscape-demo` уровень «Система» читается за < 10 с.
- **SC-02:** Вход в участника оставляет на холсте только связанные внешние узлы
  (для service — обязательно в MVP).
- **SC-03:** Cap узлов соблюдён; полного dump нет.
- **SC-04:** Пункт «Граф анализ» = прежнее поведение списков (регресс).
- **SC-05:** Редактирования канона нет.
- **SC-06:** Клик по `database` не показывает выдуманные схемы/физику — только
  данные канона + связанные сервисы.

## Предложенные ответы (на вопросы до specify)

> Статус: **предложение** — БД (§3) согласована по смыслу в обсуждении; остальное
> ждёт явной ОКции. После ОКции → FR в `spec.md`.

### 1. Что внутри service на уровне 1?

**Ответ: в MVP только system-сущности** (`http_endpoint`, `dotnet_project`, связанные
system-узлы с `parent_id` → этот service). Code (`class` / `method`) — уровень 2+,
отдельный вход «показать код» / drill, не стартовый экран сервиса.

**Почему:** уровень 1 должен остаться картой «входы и куски сервиса», а не свалкой
символов; иначе снова нужен /graph-анализ глазами.

### 2. Внешний сосед: stub или можно войти?

**Ответ: клик по внешнему соседу = смена фокуса** (войти в него как в нового
участника). Отдельная кнопка/режим не нужна: сосед на холсте уже выбран осознанно.

Stub — только **визуальный** стиль (меньше деталей, пока он «снаружи»). После
«входа» он становится фокусом, прежний фокус уходит в крошки.

**Почему:** иначе с уровня «Api» нельзя перейти к «Orders» без возврата на систему —
лишний шаг.

### 3. Drill в infra (БД, брокер)? Топики где?

#### 3a. БД — как хотим видеть (целевая модель)

В реальном коде обычно есть иерархия, а не одна «облачная БД»:

```text
Физическая БД / инстанс     (host:port, cluster, server)
  └── Логическая БД         (Database=… в connection string; catalog)
        └── Схема           (dbo / public / app_schema …)   ← часто «чья» зона сервиса
              └── (таблицы / объекты — ещё глубже, не обязательный MVP просмотра)
```

Сервис почти никогда «владеет всей физикой»: он подключается к **логической БД**
и/или к **схеме** внутри неё. На просмотре это должно читаться так:

| Уровень фокуса | Внутри | Снаружи (порты) |
|----------------|--------|-----------------|
| Физическая БД | логические БД на этом инстансе | сервисы/другие участники, связанные с любой логикой внутри |
| Логическая БД | схемы (если известны) | сервисы с `connects_to` на эту логику; родитель-физика как контекст |
| Схема | (опц.) объекты / пусто в MVP | сервис(ы), «приписанные» к схеме |

Это **совместимо** с правилом «фокус + только внешние связи».

#### 3b. Что есть в парсинге сейчас (`009`) — честно

Сейчас **нет** иерархии физика → логика → схема.

| Есть | Как |
|------|-----|
| Узел `kind=database` | Из `appsettings` (и отчасти compose infra): **одна connection string / логическое имя** → один узел |
| `metadata.engine` | postgres / mssql / redis / … |
| Ребро `connects_to` | сервис → этот `database` |
| Дедуп | одно логическое имя у разных сервисов → один узел |

Нет отдельных kinds вроде `database_instance` / `database_schema`, нет разбора
`Host` vs `Database=` vs SQL schema из CS/EF/миграций, нет «сервис владеет схемой X».

Итого: **модель из 3a — правильная цель для просмотра, но данных под полный drill
в каноне пока нет.** Это не баг черновика `011`, а пробел extract/`009`+.

#### 3c. Решение для `011` MVP + follow-up

| Слой | Решение |
|------|---------|
| **MVP `011` (на текущем каноне)** | Узел `database` = то, что уже извлекли (фактически **логическое** имя CS). На уровне 0 — peer. «Войти» → inspector (engine, key) + снаружи сервисы с `connects_to`. Пустой фейк «схемы» не рисуем. |
| **Целевой UX (зафиксировать в видении `011`)** | Drill БД по иерархии 3a, когда появятся узлы/рёбра. |
| **Данные (не смешивать с canvas-only)** | Отдельный follow-up (уточнить номер/спеку later): расширить `appsettings` (host/database из CS), опц. EF/SQL schema extract → kinds или metadata + `parent_id`. Пока этого нет — просмотр честно ограничен. |

`storage` / `external_api` в MVP — как сейчас: peer + inspector + связи, без
выдуманных внутренностей.

#### 3d. Брокер / топики (без изменений по смыслу)

| Участник | На уровне 0 | «Войти» в MVP |
|----------|-------------|----------------|
| `broker` | peer | ✅ внутри — `message_topic` (если есть), снаружи — publish/consume сервисы |
| `message_topic` | дети брокера; если брокер не извлечён — topic остаётся peer | смена фокуса |

**Почему так:** не обещаем на холсте схемы БД, которых парсер не построил; но
**закладываем** правильную модель БД в черновик, чтобы следущий extract не ломал UX.

### 4. API сразу или клиент для уровня 0?

**Ответ: сразу проектировать `GET .../graph/view`** (или эквивалент) как основной
контракт просмотра; уровень 0 не собирать N+1 с `.../edges` на large repo.

Допустимо в implement: тонкий клиентский fallback только для крошечных фикстур /
dev, но **спека и DoD** опираются на view-endpoint.

**Почему:** правило «фокус + внешние» на `010`-объёмах иначе непредсказуемо по
latency и cap.

### 5. Поиск на «Граф просмотр»?

**Ответ: в MVP нет отдельного поиска на просмотре.** Навигация: крошки, клики,
смена фокуса. Найти узел текстом — в **«Граф анализ»**, оттуда «Открыть на схеме»
(US5).

**Почему:** один экран — одна задача (смотреть карту); поиск уже сделан в `007`.

### 6. «Узел принадлежит сервису U»?

**Ответ: в MVP опираемся на то, что уже есть в `009`:**

1. **`parent_id`** — основной путь (описан: напр. `http_endpoint` → `service`).
2. Рёбра system (`exposes`, `depends_on`, …) — для внешней оболочки фокуса.
3. Code-узлы на уровне 2+: эвристика **пути** (`path` / префикс каталога сервиса) и/или
   связь через уже загруженный system-контур — **не** раздувать ingest в `011`, пока
   не упрёмся.

Если на пилоте `parent_id` дырявый для части kinds — **research в plan `011`**:
минимальный задел `metadata.service_id` (или нормализация parent при ingest) как
