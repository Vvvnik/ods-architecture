## 1. Ключевая идея (согласовано с пилотом)

1. **Не один JSON на все языки на выходе парсера.** Каждый языковой модуль может
   отдавать **свой удобный формат** (Roslyn model → JSON, TS AST → JSON, и т.д.).
2. **В Elasticsearch хранится канонический слой** — нормализованные **метаданные
   графа** (узлы, рёбра, привязка к `project_id` / `path`), а не сырой AST.
3. **Парсеры — отдельные модули** (отдельный скрипт/процесс на язык или семейство),
   не «одна каша» в одном бинарнике. Новый язык = **новый модуль**, регистрация
   в оркестраторе.
4. **Сначала — автоопределение языков** проекта; по результату запускается только
   **набор доступных** парсеров. Для языка без модуля — явный статус «не
   поддерживается», без падения всего анализа.

## 2. Два уровня данных

```text
Working Copy (002, sync)
        │
        ▼
┌───────────────────────────────────────┐
│ 005: Language Detector                │
│  → languages.json (языки + файлы)     │
└───────────────────────────────────────┘
        │
        ▼  для каждого включённого языка
┌───────────────────────────────────────┐
│ 005: Parser Module (отдельный процесс) │
│  → parser-native JSON (свой формат)    │
└───────────────────────────────────────┘
        │
        ▼  адаптер модуля или общий ingest
┌───────────────────────────────────────┐
│ 006: Canonical Graph Model → ES       │
│  nodes / edges / analysis_runs        │
└───────────────────────────────────────┘
        │
        ▼
   003: UI «Граф» (вместо заглушки)
```

| Уровень | Где живёт | Пример |
|---------|-----------|--------|
| **Сырой выход парсера** | файл / stdout / временный каталог | `csharp-extract.json`, `ts-extract.json` |
| **Отчёт детектора** | ES или файл артефакта анализа | `languages.json` |
| **Канон графа** | **Elasticsearch** (006) | `graph_nodes`, `graph_edges` (имена — в спеке) |
| **Дерево файлов** | уже есть в 002 | `elements` — не дублировать |

**Graphify** (этап 007) — **отдельный канал** со своим JSON; в 005/006 только
заложить точку расширения (adapter), не смешивать с языковыми парсерами.

## 3. Разделение: что в 005, что в 006

### `005-code-analysis` — оркестрация и парсеры

**Фокус:** как узнать языки, как запустить модули, контракт плагина.

| # | Требование (черновик) | Примечание |
|---|------------------------|------------|
| D-005-1 | **Language Detector** после sync (или по кнопке «Анализ»): обход WC, эвристики по расширениям + опционально shebang/`package.json`/`*.csproj` | выход: `languages.json` |
| D-005-2 | В `languages.json`: список языков, число файлов, примеры путей, **статус парсера** (`available` / `missing` / `failed`) | для UI и логов |
| D-005-3 | **Реестр парсеров**: id, поддерживаемые языки, команда запуска, версия схемы native JSON | конфиг или каталог `parsers/` |
| D-005-4 | Каждый парсер — **отдельный исполняемый модуль** (CLI): вход `project_id`, `working_copy_root`, список файлов или glob; выход — **native JSON** + код возврата | не монолит |
| D-005-5 | Оркестратор в backend (TypeScript MVP): параллель/очередь запуска модулей, таймауты, логи | async, как sync |
| D-005-6 | MVP-парсеры (минимум): **TypeScript/JavaScript** (один модуль); **C#** — второй приоритет или follow-up | по объёму спеки |
| D-005-7 | Инкрементальный анализ (только изменённые файлы) — **желательно**, не обязателен в первой итерации 005 | post-MVP в 005 или 006 |
| D-005-8 | Не хранить native JSON в ES как основной артефакт (опционально — debug volume) | ES = канон 006 |

**Independent test 005:** после sync проекта на TS+CS репо детектор выдаёт оба языка;
запускается TS-парсер; для C# без модуля — `missing`, остальное не падает.

### `006-project-graph` — модель графа и потребление

**Фокус:** канонические узлы/рёбра в ES, API, связь с порталом.

| # | Требование (черновик) | Примечание |
|---|------------------------|------------|
| D-006-1 | **Каноническая модель** узла и ребра (kind, id, name, language, path, location, metadata) | см. `canonical-graph-model.md`, упростить под ES |
| D-006-2 | Индексы ES (или расширение 002): `graph_nodes`, `graph_edges`, опционально `analysis_runs` | всегда фильтр `project_id` |
| D-006-3 | **Ingest pipeline**: native JSON парсера → маппинг в канон (адаптер на модуль или общий с `parser_id`) | не один формат на входе адаптера |
| D-006-4 | REST API: запуск анализа, статус, получение подграфа / списка узлов по файлу | расширение OpenAPI 002 |
| D-006-5 | Связь с деревом 002: узел графа ссылается на `element_id` или `path` | навигация файл ↔ граф |
| D-006-6 | UI 003: заменить заглушку «Граф» — минимум список узлов / простая визуализация | детали в 003 или 006 |
| D-006-7 | Удаление проекта (002 DELETE) **каскадирует** документы графа | согласовать с US5 002 |
| D-006-8 | Версионирование прогона анализа (`analysis_run_id`, `completed_at`) | для повторного анализа |

**Independent test 006:** после 005 ingest в ES есть узлы/рёбра; API отдаёт зависимости
для выбранного файла; DELETE проекта очищает граф.

## 4. Модульный парсер (контракт, эскиз)

Каждый модуль в каталоге вида `parsers/<parser-id>/`:

```text
parsers/
  typescript/
    manifest.json      # id, languages[], schema_version, command
    run.sh | run.mjs   # CLI
    README.md
  csharp/
    ...
```

**manifest.json (черновик полей):**

| Поле | Описание |
|------|----------|
| `id` | `typescript`, `csharp`, … |
| `languages` | `["typescript", "javascript"]` |
| `schema_version` | версия **native** JSON |
| `command` | как вызвать из оркестратора |
| `input` | `working_copy_root`, `files[]`, `project_id` |
| `output` | путь к native JSON |

**Оркестратор не знает AST** — только запуск, проверка exit code, передача в ingest 006.

## 5. Language Detector — выход `languages.json` (эскиз)

```json
{
  "project_id": "uuid",
  "detected_at": "ISO-8601",
  "languages": [
    {
      "language": "typescript",
      "file_count": 42,
      "sample_paths": ["src/app.ts"],
      "parser_id": "typescript",
      "parser_status": "available"
    },
    {
      "language": "csharp",
      "file_count": 10,
      "sample_paths": ["Program.cs"],
      "parser_id": "csharp",
      "parser_status": "missing"
    }
  ]
}
```

Детектор **не парсит AST** — только классификация файлов по правилам.

## 7. Вне scope первой итерации 005/006

- Graphify (007) — только hook adapter
- RAG, векторный поиск (009)
- Полный graph viewer (React Flow) — минимальный UI достаточно
- Auth, очереди (Redis/Kafka)
- .NET backend для Roslyn — **возможен отдельный parser module** (subprocess), не смена стека 002
- Единый «unified JSON» на выходе каждого парсера — **отклонено**; канон только на уровне 006 / ES
