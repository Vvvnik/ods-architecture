## 1. Ключевая идея (согласовано с пилотом)

1. **Не один JSON на все языки на выходе парсера.** Каждый языковой модуль может отдавать **свой удобный формат** (Roslyn model → JSON, TS AST → JSON, и т.д.).
2. **В Elasticsearch хранится канонический слой** — нормализованные **метаданные графа** (узлы, рёбра, привязка к `project_id` / `path`), а не сырой AST.
3. **Парсеры — отдельные модули** (отдельный скрипт/процесс на язык или семейство), не «одна каша» в одном бинарнике. Новый язык = **новый модуль**, регистрация в оркестраторе.
4. **Сначала — автоопределение языков** проекта; по результату запускается только **набор доступных** парсеров. Для языка без модуля — явный статус «не поддерживается», без падения всего анализа. 
5. **Общая обёртка (envelope)** для всех парсеров — единый минимальный контракт CLI; поле **`model`** внутри — **свободное**, свой формат у каждого модуля.
6. **Не один JSON на весь проект** от языковых парсеров — отдельный артефакт на модуль. Слияние — в **006 / ES**.

## 2. Три уровня данных

```text
Working Copy (002, sync)
        │
        ▼
┌───────────────────────────────────────┐
│ 005: Language Detector                │
│  → languages.json (языки + файлы)     │
└───────────────────────────────────────┘
        │
        ▼  для каждого включённого языка
┌───────────────────────────────────────┐
│ 005: Parser Module (отдельный процесс) │
│  → envelope JSON (model = native)      │
└───────────────────────────────────────┘
        │
        ▼  адаптер модуля или общий ingest
┌───────────────────────────────────────┐
│ 006: Canonical Graph Model → ES       │
│  nodes / edges / analysis_runs        │
└───────────────────────────────────────┘
        │
        ▼
   003: UI «Граф» (вместо заглушки)
```

| Уровень | Где живёт | Одинаковый формат? | Пример |
|---------|-----------|-------------------|--------|
| **1. Envelope парсера** | ES (привязка к `project_id`) | **да** (обёртка) | см. §4.1 |
| **1b. Native `model`** | внутри envelope в ES | **нет** (свой у каждого парсера) | Roslyn extract, TS symbols |
| **2. Артефакты прогона** | ES, по одному на модуль | несколько документов | `analysis_runs` + payload парсера |
| **Отчёт детектора** | ES | один на прогон | отчёт по языкам (`languages.json`) |
| **3. Канон графа** | **Elasticsearch** (006) | **да** (единая модель) | `graph_nodes`, `graph_edges` |
| **Исходники проекта** | Docker volume / mount в контейнере (`ods-data`, `/repos`) | — | только сырые файлы после sync |
| **Дерево файлов** | уже есть в 002 (ES) | — | `elements` — не дублировать |

#### 3.1 UX подтверждения анализа (после sync / импорта)

Определение языков — **автоматически**. Парсеры сами не стартуют.

**Окно 1 — языки проекта:**

- Список из отчёта (сверху — больше файлов).
- **Новый проект:** без подсветки «новизны».
- **Повторный sync:** новые языки — **красным** (нет парсера) или **зелёным** (парсер есть).
- **«Продолжить»** → окно 2; **«Отмена»** → парсеры не запускаются.

**Окно 2 — изменения в коде** (после «Продолжить» в окне 1):

- Были ли правки с прошлого sync (добавлены, изменены, удалены).
- **«Продолжить»** → запуск парсеров для языков с доступным парсером.
- **«Отмена»** → парсеры не запускаются, прежний результат анализа сохраняется.

## 4. Модульный парсер (контракт)

### 4.1 Envelope JSON — общий для всех парсеров (005)

Оркестратор **MUST** понимать только обёртку; содержимое `model` — зона ответственности
модуля и его адаптера в 006.

```json
{
  "parser_id": "typescript",
  "schema_version": "1",
  "project_id": "uuid",
  "analysis_run_id": "uuid",
  "generated_at": "ISO-8601",
  "files_analyzed": ["src/app.ts", "src/utils.ts"],
  "model": {}
}
```

| Поле | Обязательно | Описание |
|------|-------------|----------|
| `parser_id` | да | совпадает с `manifest.json` → `id` |
| `schema_version` | да | версия **native** схемы внутри `model` |
| `project_id` | да | проект из 002 |
| `analysis_run_id` | да | прогон анализа (006) |
| `generated_at` | да | ISO-8601 |
| `files_analyzed` | да | пути относительно WC |
| `model` | да | **свободный** JSON: extract Roslyn, TS symbols, и т.д. |

Парсер **MUST NOT** требовать от оркестратора знания структуры `model`.

### 4.2 Каталог модуля

Каждый модуль в каталоге вида `parsers/<parser-id>/`:

```text
parsers/
  typescript/
    manifest.json      # id, languages[], schema_version, command
    run.sh | run.mjs   # CLI
    README.md
  csharp/
    ...
  python/
    ...
  cpp/
    ...
```

**Целевой набор модулей (005):** `typescript`, `csharp`, `python`, `cpp`. Прочие языки —
новый модуль в реестре по мере надобности.

**manifest.json (черновик полей):**

| Поле | Описание |
|------|----------|
| `id` | `typescript`, `csharp`, `python`, `cpp`, … |
| `languages` | `["typescript", "javascript"]` |
| `schema_version` | версия **native** JSON |
| `command` | как вызвать из оркестратора |
| `input` | `working_copy_root`, `files[]`, `project_id` |
| `output` | путь к **envelope** JSON |

**Оркестратор не знает AST и не знает `model`** — только envelope, exit code, передача в ingest 006.

## 5. Language Detector — выход `languages.json` (эскиз)

```json
{
  "project_id": "uuid",
  "detected_at": "ISO-8601",
  "languages": [
    {
      "language": "typescript",
      "file_count": 42,
      "sample_paths": ["src/app.ts"],
      "parser_id": "typescript",
      "parser_status": "available"
    },
    {
      "language": "python",
      "file_count": 28,
      "sample_paths": ["src/train.py", "lib/utils.py"],
      "parser_id": "python",
      "parser_status": "available"
    },
    {
      "language": "cpp",
      "file_count": 15,
      "sample_paths": ["native/bindings.cpp"],
      "parser_id": "cpp",
      "parser_status": "available"
    },
    {
      "language": "csharp",
      "file_count": 10,
      "sample_paths": ["Program.cs"],
      "parser_id": "csharp",
      "parser_status": "available"
    },
    {
      "language": "go",
      "file_count": 2,
      "sample_paths": ["tools/helper.go"],
      "parser_id": null,
      "parser_status": "missing"
    }
  ]
}
```

Детектор **не парсит AST** — только классификация файлов по правилам.

Языки в массиве `languages` **сортируются по `file_count` по убыванию** (больше файлов —
выше в списке). Тот же порядок: показ в UI (§3.1) и запуск парсеров оркестратором.
При равном `file_count` — по имени языка (алфавит).
